# loft: 강판을 자르기 전에 선형을 띄운다

## Purpose

- 말이 막힌 디자인 질문 — 두 개의 그럴듯한 답, 대화로는 반증 불가 — 을 **저렴한 실행 가능 아티팩트**로 확인한다.
- 역할 계약: crew가 아티팩트를 만들고, captain의 유일한 일은 **반응**이다. 그 반응이 곧 결정. 아티팩트는 보는 도구이지, 산출물의 선행 작업이 아니다.

## Workflow

### 1. Loft할 때 / 안 할 때

**할 때**: 디자인 질문이 말에서 막힐 때 ("경로 페이지는 어떻게 보여야 하지", "이 상태 모델이 맞는 느낌인가") / navigator 지도의 `loft` 티켓 / 스펙 논의가 "봐야 알겠다"에 도달.

**안 할 때**: 레포 증거로 답하거나 captain에게 물으면 되는 것 (그건 인터뷰) / 목적지 자체가 불명확 (그건 fog — ask-navigator) / 이미 ADR에 정해진 결정 / 사실은 버그 (디버거 관할).

### 2. 포크 선택 (질문이 묻는 것에 따라)

**Logic 포크 — 모델이 맞는가?** (상태·규칙·데이터 형태·알고리즘)
1. 결정의 핵심 — 상태 머신·리듀서·스키마·알고리즘 — 을 **순수 모듈**로 분리 (DOM·I/O·프레임워크 없음). 확정되면 그대로 실제 코드베이스로 옮길 수 있게 작성.
2. 클릭 가능한 단일 HTML 셸로 감싸기: 시나리오당 버튼 하나, 까다로운 엣지 케이스 순서대로, 클릭마다 전체 상태 표시.
3. 확정된 모듈은 나중에 launch를 통해 실제 작업으로 재진입. loft 중 `main`은 손대지 않고 셸은 브랜치에 둔다.

**UI 포크 — 어떻게 보여야 하는가?** (형태·배치)
1. 한 라우트, **구조가 다른 변형 3종** — 정보 구조·내비게이션 모델·밀도. 스타일만 다른 3종은 벽지다.
2. 페이지 내 스위처로 변형 전환. 가능하면 기존 제품에 임베드해 실제 데이터 밀도로 검증.
3. 확정되면 **결정**만 이전하고 변형은 브랜치에 기록으로 남긴다.

### 3. 규율

- 실행은 한 명령 — 레포의 가장 단순한 기존 serve 명령. 빌드 스텝 없음, 수 초 내 로드.
- 영속화·테스트·추상화 없음. **출하하고 싶지 않은 것**이어야 한다.
- 첫 형태는 논쟁 대상: 같은 세션에 브랜치에서 수정. captain이 **최종** 형태를 확인한 것이 결정.
- 아티팩트 수명은 수 분 제작 + 한 세션 결정. 프로덕션 코드로 자라기 시작하면 중단 — 그건 launch 작업이다.
- 하나의 loft는 **하나의 질문**에 답한다.

### 4. 답 접기

1. 결정이 사는 곳에 기록 — 이슈 코멘트, 스펙의 Implementation Decisions, captain의 말 + 이유 한 줄. lofted 표시와 함께 리듀서·상태 머신 등 정밀한 단편은 인라인 가능.
2. 아티팩트는 `loft/<name>` 브랜치에 푸시. **머지 금지** — 나중에 "왜"를 볼 수 있는 1차 출처로 남는다.
3. 아티팩트의 어떤 줄도 `main`에 들어가지 않는다.

## Output Contract

- captain의 반응 (결정) + 결정이 기록된 위치 + `loft/<name>` 브랜치의 아티팩트 포인터.

## Operating Rules

- 한계: captain의 반응만이 유일한 승인. loft가 스스로 답을 승인하지 않는다.
- 범위: loft는 답을 생산하지 산출물을 생산하지 않는다. 진단(디버거)·fog 차트(ask-navigator)·테스트 심 승인(C2)은 관할 밖.
- 완료 정의: captain이 반응했고, 답이 결정의 위치에 있고, 아티팩트가 브랜치에 있고, 아티팩트의 어떤 줄도 `main`에 없다.
