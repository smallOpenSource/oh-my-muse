# 체계적 디버깅

## 개요

**핵심 원칙:** 수정 시도 전에 반드시 근본 원인을 먼저 찾는다. 증상 수정은 실패다.

**이 절차의 문자를 어기는 것은 정신을 어기는 것이다.**

## 철칙

```
근본 원인 조사 없이 수정 금지
```

Phase 1을 끝내지 않았으면 수정안을 제안할 수 없다.

## 사용 시점

모든 기술적 이슈에 사용: 테스트 실패, 프로덕션 버그, 예상 밖 동작, 성능 문제,
빌드 실패, 통합 이슈.

**특히 사용할 때:**
- 시간 압박 (긴급할수록 추측이 유혹적)
- "빠른 수정 하나"가 자명해 보일 때
- 이미 여러 수정을 시도했을 때
- 이전 수정이 통하지 않았을 때
- 이슈를 완전히 이해하지 못할 때

**건너뛰지 말 것:**
- 단순해 보이는 이슈 (단순한 버그에도 근본 원인이 있다)
- 서두를 때 (서두르면 재작업이 확정)
- "지금 당장 고쳐"라는 요구 (체계적이 추측 난타보다 빠르다)

## 네 단계

각 단계는 다음으로 가기 전에 끝내야 한다.

### Phase 1: 근본 원인 조사

**어떤 수정 시도 전:**

1. **에러 메시지를 주의 깊게 읽는다.** 건너뛰지 않는다. 스택 트레이스를 끝까지 읽는다. 줄 번호·파일 경로·에러 코드를 적는다.

2. **일관되게 재현한다.** 믿을 만하게 트리거할 수 있는가? 정확한 단계는? 매번 일어나는가? 재현 불가 → 데이터를 더 모은다, 추측 금지.

3. **최근 변경을 확인한다.** 무엇이 바뀌었길래 이럴 수 있는가? git diff·최근 커밋·새 의존성·설정 변경·환경 차이.

4. **다중 컴포넌트 시스템에서는 증거를 모은다.** 수정 제안 전에 진단 계측을 추가한다:
   ```
   각 컴포넌트 경계마다:
     - 무엇이 들어가는지 로그
     - 무엇이 나가는지 로그
     - 환경/설정 전파 확인
     - 각 계층의 상태 확인
   한 번 실행해 어디서 깨지는지 보여주는 증거 수집
   그 다음 증거를 분석해 실패 컴포넌트 특정
   그 다음 그 컴포넌트를 조사
   ```

5. **데이터 흐름을 추적한다.** 콜 스택 깊숙한 에러라면: 이 디렉토리의 `root-cause-tracing.md`에 완전한 역방향 추적 기법이 있다. 나쁜 값이 어디서 비롯됐는지, 무엇이 그 값으로 호출했는지 계속 위로 추적한다. 증상이 아닌 원인 지점에서 고친다.

### Phase 2: 패턴 분석

**수정 전에 패턴을 찾는다:**

1. 동작하는 예시를 찾는다 — 같은 코드베이스의 유사한 동작 코드.
2. 레퍼런스와 비교한다 — 패턴을 구현 중이라면 레퍼런스 구현을 전부 읽는다. 훑지 말고 한 줄 한 줄.
3. 차이를 특정한다 — 동작하는 것과 깨진 것의 모든 차이. "그건 상관없겠지" 금지.
4. 의존성을 이해한다 — 무엇이 필요한지, 어떤 설정·환경·가정을 하는지.

### Phase 3: 가설과 테스트

**과학적 방법:**

1. 단일 가설을 세운다 — "X가 근본 원인이라고 생각한다. Y 때문이다." 적는다. 구체적으로.
2. 최소로 테스트한다 — 가설을 테스트하는 가장 작은 변경. 한 번에 하나의 변수. 여러 개를 한꺼번에 고치지 않는다.
3. 계속하기 전에 검증한다 — 됐으면 Phase 4, 안 됐으면 새 가설. 위에 수정을 더 쌓지 않는다.
4. 모르면 "X를 이해하지 못했다"고 말한다. 아는 척 금지. 도움을 요청한다. 더 조사한다.

### Phase 4: 구현

**근본 원인을 고친다, 증상이 아니라:**

1. 실패하는 테스트 케이스를 만든다 — 가장 단순한 재현. MUST. 테스트 작성은 test-driven-development 스킬을 사용한다.
2. 단일 수정을 구현한다 — 파악한 근본 원인을 다룬다. 한 번에 하나. "겸사겸사" 개선 금지. 묶음 리팩터링 금지.
3. 수정을 검증한다 — 테스트가 통과하는가? 다른 테스트가 깨지지 않았는가? 이슈가 실제로 해결됐는가? 성공을 주장하기 전에 verification-before-completion 스킬을 사용한다.
4. **수정이 통하지 않으면 멈춘다.** 시도한 수정이 몇 개인지 센다. 3개 미만이면 Phase 1로 돌아가 새 정보로 재분석. **3개 이상이면 아키텍처를 의심한다 (아래 5번).** 아키텍처 논의 없이 4번째 수정 시도 금지.
5. **3개 이상 실패하면 아키텍처를 묻는다.** 각 수정이 다른 곳의 새 공유 상태·결합·문제를 드러내거나, "대규모 리팩터링"이 필요하거나, 각 수정이 다른 곳에 새 증상을 만들면 — 패턴 자체가 잘못된 것이다. 멈추고 근본을 묻는다: 이 패턴이 근본적으로 타당한가? 관성으로 붙잡고 있는가? 증상을 계속 고칠 것인가 아키텍처를 리팩터할 것인가? **더 수정하기 전에 상대방과 논의한다.**

## 경고 신호 — 멈추고 절차를 따르라

- "일단 빨리 고치고 나중에 조사하자"
- "X만 바꿔보고 되나 보자"
- "여러 개를 한꺼번에 바꾸고 테스트 돌리자"
- "테스트는 건너뛰고 수동으로 확인하자"
- "아마 X일 거야, 고치자"
- "완전히 이해는 안 되지만 이게 통할지도"
- "하나만 더 시도" (이미 2번 이상 시도했을 때)
- **각 수정이 다른 곳의 새 문제를 드러낸다**

**전부 Phase 1로 돌아가라는 뜻이다.**

## 상대방이 잘못하고 있다고 알리는 신호

- "그거 안 일어나고 있는 거 아니야?" — 검증 없이 가정했다
- "추측 그만" — 이해 없이 수정안을 제안하고 있다
- "우리가 막혔어?" (짜증) — 접근이 통하지 않는다

**이런 신호가 보이면:** 멈춘다. Phase 1로 돌아간다.

## 흔한 합리화

| 변명 | 현실 |
|------|------|
| "이슈가 단순하니 절차 불필요" | 단순한 이슈에도 근본 원인이 있다. 단순한 버그에 절차는 빠르다. |
| "긴급해서 절차할 시간 없어" | 체계적 디버깅이 추측 난타보다 빠르다. |
| "일단 이거 시도하고 조사하자" | 첫 수정이 패턴을 정한다. 처음부터 옳게 한다. |
| "수정 확인되면 테스트 쓰자" | 테스트 없는 수정은 붙지 않는다. 먼저 쓴 테스트가 증명한다. |
| "한꺼번에 여러 개 고치면 시간 절약" | 무엇이 통했는지 격리 불가. 새 버그를 만든다. |
| "문제가 보이니 고치자" | 증상을 보는 것 ≠ 근본 원인을 이해하는 것. |
| "하나만 더 시도" (2회 실패 후) | 3회 실패 = 아키텍처 문제. 패턴을 묻지 말고 또 고치지 않는다. |

## 빠른 참조

| 단계 | 핵심 활동 | 성공 기준 |
|------|----------|----------|
| **1. 근본 원인** | 에러 읽기, 재현, 변경 확인, 증거 수집 | 무엇·왜를 이해 |
| **2. 패턴** | 동작 예시 찾기, 비교 | 차이 특정 |
| **3. 가설** | 이론 세우기, 최소 테스트 | 확정 또는 새 가설 |
| **4. 구현** | 테스트 만들기, 수정, 검증 | 버그 해결, 테스트 통과 |

## "근본 원인 없음"이 드러났을 때

정말로 환경·타이밍·외부 문제라면: 절차를 끝낸 것, 조사한 것을 문서화하고, 적절한 처리(재시도·타임아웃·에러 메시지)를 구현하고, 향후 조사를 위한 모니터링·로깅을 추가한다. **단, "근본 원인 없음"의 95%는 불완전한 조사다.**
