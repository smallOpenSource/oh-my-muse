# TDD

작은 단계의 red-green — 합의된 seam에서만. launch 실행에서는 seam 목록이 C2(수락 기준 + 테스트 경계 승인)의 승인 산출물이다. launch 밖에서는 첫 테스트가 존재하기 전에 사용자와 seam을 합의한다 — **승인받지 않은 seam에는 테스트를 붙이지 않는다.**

## The loop

테스트 하나 → 구현 하나 → 반복:

1. seam에 다음 테스트를 쓴다. 돌린다. **예상한 이유로 실패하는 것을 본다** — 실패할 수 없는 테스트는 테스트가 아니다.
2. green으로 바꾸는 가장 작은 변경을 구현한다.
3. 반복. 각 테스트는 tracer bullet이다 — 동작을 관통하는 좁지만 완전한 경로지, 한 레이어를 고립시켜 끝내는 것이 아니다.

## Rules

- 기대값은 **독립된 진실 출처**에서 온다 — 스펙 한 줄, 손으로 풀어본 예제, 문서화된 출력. 테스트 대상 구현에서 가져오지 않는다: 코드가 하는 일을 그대로 단언하는 테스트는 검사가 아니라 거울이다.
- 대체(substitute)는 seam이 선언한 **경계 클래스**에서만 — in-process, locally substitutable, owned-remote 포트, true-external. C2가 각 seam에 기록한 클래스다. 테스트가 운동하는 경계 안쪽에는 대체물을 두지 않는다.
- 리팩터링은 루프의 일부가 아니다. 리뷰 단계의 일이고, 고치는 쪽이 소유한다. red-green 중간에 리팩터하지 않는다.
- 버그 수정은 그 버그를 재현하는 **실패 테스트부터** — 이론보다 재현이 먼저. debug 스킬의 규칙이다.
- seam을 제안할 때는 한 줄로 말한다 — 무엇을 잡고 무엇을 통과시키는지. 가격을 매길 수 없는 seam 선택은 결정이 아니라 추측이다.

## When no seam fits

승인된 어떤 seam에서도 테스트할 수 없는 동작이면 멈추고 그대로 말한다: 빠진 seam을 발견으로 보고한다(`architecture-survey`와 `refit`의 투입구가 된다). seam을 지어내거나 내부를 관통해 테스트하지 않는다.

## Output Contract

- 사용한 seam 목록 — 경계 클래스 + 각 seam의 catch/miss 한 줄
- Red/green 증거 — 실패 실행과 통과 실행
- seam 부재 발견 (있을 때)

## Operating Rules

- launch 안에서는 C2 승인 seam 목록을 따른다(경계 클래스는 `launch` 스킬의 C2 섹션 참조). launch 밖에서는 사용자와 seam을 먼저 합의한다.
- 한 번에 하나의 테스트 — 실패 원인을 예상하고 확인한 뒤에만 구현으로 넘어간다.
- 기대값을 구현에서 역산하지 않는다. 스펙·예제·문서에서 가져온 값만 쓴다.
