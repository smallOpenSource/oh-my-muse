# Launch

## Purpose

미션 브리프부터 검증된 변경까지의 딜리버리 파이프라인을 실행한다. 원칙은 **검증 가능성 경계**: 시스템이 검출·재실행·롤백할 수 있는 반복 작업은 에이전트가 연속 실행하고, 정답이 유일하지 않거나 실패 비용이 큰 결정은 사람이 체크포인트에서 결정한다. 최대 자동화가 아니라 검증 가능한 작업의 최대 위임이 목표다 — 사람은 오직 사람만 내릴 수 있는 결정에 시간을 쓴다.

**검증 가능성 테스트** (모든 단계에 적용): "이것이 잘못되면 시스템이 검출할 수 있는가? 자동으로 다시 하거나 롤백할 수 있는가?" 둘 다 예 → 에이전트. 정답이 유일하지 않거나, 시스템이 판단 불가거나, 잘못되면 비용이 크다 → 사람.

### 체크포인트 역할 분담

| 사람 체크포인트 (결정 20%) | 에이전트 연속 실행 (반복 80%) |
|---|---|
| C1 미션 브리프 작성(목표+범위) | 팩트 수집·레포 탐색(자가 조달) |
| C2 수락 기준 + 테스트 경계(seam) 승인 | 프론티어 질문 묶음 + 권장안 준비 |
| C3 티켓 분해(입도·차단 엣지) 승인 | 스펙·티켓 초안 + 기계 검증 |
| C4 실행 중 부상하는 비가역 결정 일괄 답변 | seam에서 TDD 구현, 빌드·테스트·회귀 |
| C5 완료 보고서 수락 | 코드 리뷰, 전체 검증, 페이퍼 트레일 |

## Workflow

### Phase 0 — 진입 (야드 게이트)

호출 시 가장 먼저 워크스페이스 준비 상태를 점검한다 (원본의 drydock `--check` 감사 대체):

- `CONTEXT.md`(용어집) 존재 여부, `docs/adr/`·`docs/business/` 슬롯 존재 여부, 깨진 경로 참조 여부.
- **조치 가능한 고신뢰 findings가 있으면 실행을 차단**: findings를 그대로 나열하고, 실행이 시작되지 않았으며 아티팩트가 생성되지 않았음을 밝히고 중단한다. 명시적 사용자 재지시가 없는 한 모든 finding을 차단으로 간주한다.
- 명시적 의도가 있을 때만 좁은 범위 오버라이드 가능 (저신뢰 finding, 명시적 false positive, 사용자가 선언한 스크래치 레포). 고신뢰 finding을 조용히 넘기지 않는다.
- 통과(또는 오버라이드) 시에만 진행. Launch는 슬롯(`CONTEXT.md`, `docs/adr/`, `docs/business/`)을 만들지 않고 이미 존재하는 슬롯을 채운다.

### Phase 1 — 수렴 (사람이 결정, 에이전트가 준비)

- 브리프 자가 점검: 목표·범위 경계·non-goals 중 2개 이상이 빠졌으면 지적하고 한 차례 다듬기를 요청한다.
- **포그 게이트**: Q1 "목적지를 한 문장으로 말할 수 있는가?" Q2 "지금 당장 답할 수 없더라도 첫 세 결정을 정확히 말할 수 있는가?" 둘 중 하나라도 아니오 → 실행하지 않고, 아티팩트 없음을 밝히고, 목표를 질문으로 명확화하는 대화(원본의 ask-navigator 내비게이터 역할)를 제안하고 중단한다.
- 프론티어 라운드 인터뷰: 현재 물을 수 있는 질문을 한 라운드에 묶어 번호 매겨 제시하고, 각 질문에 권장 답을 첨부한다. 사람이 답하면 트리를 재구성한다. 팩트는 서브에이전트가 레포 증거에서 자가 조달 — 사람에게는 탐색으로 해결 안 되는 것만 묻는다.
- **이해 리셋**: 결정안을 확정 전에 CONTEXT.md 용어로 짧게 바꿔 말해 확인받는다. 잘못 이해된 메시지는 짧고 평이하게 다시 보내고 나서 진행한다.
- 확정 즉시 페이퍼 트레일 기록: 용어 → `CONTEXT.md`, ADR급 결정(되돌리기 어렵거나 맥락 없이 놀라운 트레이드오프) → `docs/adr/NNNN-<slug>.md`, 비즈니스 규칙·배경 → `docs/business/`.
- 수렴 실패는 정상: 남은 질문을 순위 매겨 제시한다(C2 입력). 남은 질문 자체가 정확히 서술 불가면 포그 게이트로 돌아가 중단한다.
- **확정 합의 종료**: 이미 결정이 내려진 세션에서 이 호출이 오면(전 대화에서 결정 트리가 다 작업됨 — 모든 프론티어 질문에 답, 용어·결정 확정) Phase 1을 **합의 감사**로 축소한다. 확정된 결정을 증거와 대조 검증하고, 전체를 한 번 다시 바꿔 말한 뒤 스펙 초안으로 간다. 질문을 다시 묻지 않는다. 단, 포그 게이트와 C2 승인은 생략하지 않는다. 바꿔 말하기(restatement)가 실패한 결정은 다시 인터뷰로 돌아간다.

### Phase 2 — 스펙 합성 (에이전트 초안 → C2 승인)

`.omc/specs/<feature-slug>/spec.md`를 합성한다 (Problem / Solution / User Stories(테스트 가능한 수락 기준) / Implementation Decisions / Testing Decisions(외부 동작만) / Out of Scope). 초안 완성 후 **C2**: 수락 기준과 테스트 경계(seam) 목록을 사람에게 승인받는다. 승인되지 않은 seam에는 테스트를 붙이지 않는다.

- **내구성 게이트**: 스펙·티켓은 계약(contract)을 담고 좌표(파일 경로·라인 번호)를 담지 않는다. 결정은 스펙 문장 안에 살고, 좌표는 증거에만 남는다.
- **경계 클래스**: 각 seam은 경계 클래스를 선언한다 — in-process, locally substitutable, owned-remote(프로덕션·테스트 어댑터가 있는 포트), true-external(주입형 대체물). 클래스가 테스트 방식을 결정한다.
- **고아 테스트 퇴역**: seam이 깊어지거나 교체되면 구 인터페이스에 붙은 테스트도 함께 퇴역한다. 새 테스트는 새 인터페이스에만 쓴다.
- **Tender 규칙**: 인터페이스 형태 자체가 논쟁 중이면(두 후보 설계, 대화로 결말 불가) C2에서 대안 사이를 선택하게 한다 — 강조점별(최소 인터페이스 면적 / 최대 미래 적합 / 주요 호출자의 최단 경로 / 가장 깔끔한 경계 어댑터)로 병렬 초안을 만들고, 나란히 비교 제시 후 사람이 선택하거나 혼합안을 접는다.

### Phase 3 — 티켓 분해 (에이전트 초안 → C3 승인)

`.omc/specs/<feature-slug>/tickets/` 아래 `NN-slug.md`로 수직 슬라이스 분해. 각 티켓은 `blockedBy: [ids]`를 선언하고, 모든 레이어를 관통하며, 독립 시연 가능하고, 하나의 fresh 컨텍스트에 들어간다. **차단 엣지는 선언 의무**: 무엇을 기다리는지(결정·아티팩트·다른 티켓)를 명시한다. 에이전트 기계 검증(독립성·시연 가능성·컨텍스트 적합성) 후 **C3**: 입도·차단 엣지·병합/분할안을 승인받는다. 승인된 티켓은 `ready-for-agent`로 표시한다. C3 기준: fresh 워커가 질문 없이 시작할 수 있어야 한다.

- **통합 배선 규칙**: 각 수직 슬라이스는 자체 배선과 smoke assertion을 포함한다. 아무것도 마운트·서빙·임포트하지 않는 슬라이스는 미완성이다. 어느 슬라이스도 소유하지 않는 크로스 슬라이스 배선(라우트 마운트·정적 서빙·진입점)은 별도 통합 티켓을 프론티어 마지막에 둔다.
- **expand-contract**: 넓은 리팩터는 "새 형태 추가 → 배치별 마이그레이션 → 구 형태 제거" 순서로, 각 배치가 하나의 티켓.

### Phase 4 — 프론티어 실행

프론티어 = 차단 요소가 모두 완료된 티켓 집합.

- **스카우트 패스**: 2개 이상 티켓이 공유하는 탐색은 배포 전에 한 번만 수행한다. 서브에이전트가 공유 질문을 해결하고 결과를 보고 — 노트는 대화에만 두고 디스크에 쓰지 않는다. 한 티켓만 필요로 하는 질문은 그 티켓에 둔다.
- **병렬(기본, 2+ 티켓)**: 티켓마다 서브에이전트를 병렬 실행(`subagent.spawn`), `blockedBy` 엣지를 작업 지시에 포함. 각 워커는 C2에서 승인된 seam에서 TDD로 구현한다. 티켓 종료 조건: 리뷰어의 코드 리뷰 통과 (구현자가 셀프 승인 금지).
- **직렬(단일 티켓 또는 `--serial`)**: 티켓을 하나씩 서브에이전트에 위임, 동일 리뷰 게이트.
- **2축 리뷰 게이트**(병렬·분리 보고, 합산 금지): 표준 축(관련 `docs/standards/` 대비 diff) + 스펙 축(이 티켓의 수락 기준 대비 diff — 누락·부분 구현·요구하지 않은 동작). 어느 한 축이라도 실패하면 티켓 실패.
- **수리 규칙**: 리뷰 판정은 리뷰어가, 수리는 단일 repair 워커가 맡는다. 리뷰어는 수리하지 않고, 구현자는 셀프 승인하지 않는다. 수리 후에는 같은 게이트를 다시 통과한다.
- **C4 — 실행 중 부상하는 결정**: ADR급 결정이 나오면 워커는 결정 의존 변경 전에 멈추고, 질문(선택지·권장안·가역성 메모)을 `.omc/specs/<feature-slug>/decisions-pending.md`에 기록한 뒤 종료한다. 이는 터미널 상태다: 작업을 재오픈하거나 후속 작업을 자동 생성하지 않는다. 이후 명시적 Launch 호출에서 사람이 C4 질문 일괄 답변 → 프론티어 재구성 후 재개한다.
- **3회 반복 실패**: 같은 검증 실패가 3회 수리 시도를 살아남으면 해당 레인을 중단하고 사람에게 근본 원인 가설을 보고한다 (C4 일괄 처리를 즉시 깨는 유일한 조건).

### Phase 5 — 종료 (에이전트 보고 → C5 수락)

- 모든 티켓 종료 + 증거 → 전체 변경에 대해 verify 실행.
- 페이퍼 트레일 정합: CONTEXT.md 정확성, ADR 완결, 구현이 가르쳐준 내용을 스펙에 반영.
- 야드 재점검: 진입 시점 대비 새 findings는 **야드 드리프트**로 보고.
- **침전물(sediment) 패스**: "이번 실행이 야드에 무엇을 가르쳤는가?" 구조화 회고(만든 것·깨진 것·배운 것·환경 마찰) 후 각 교훈을 `교훈 → 슬롯 → 의도된 변경`으로 제안하거나 명시적 사유와 함께 기각한다. 교훈이 없으면 "no new lessons"라고 그대로 말한다. 슬롯 표: 용어집 → `CONTEXT.md`, 검증 가능한 행동 규칙 → `docs/standards/`, 되돌리기 어려운 결정 → `docs/adr/`, 비즈니스 규칙 → `docs/business/`, 재사용 공예 → `.omc/skills/`(skillify 게이트 경유), 슬롯 없음 → 명시적 기각. 교훈 목록은 완료 보고서에 실어 각 줄을 개별 거부 가능하게 한다. 수락된 것만 승인 후 슬롯에 기록한다. 기록 전에는 `agent-doc-discipline` 스킬의 규칙을 적용한다.
- 완료 보고서: 출시 범위, 검증 증거, 페이퍼 트레일 위치, 야드 드리프트, 침전물 목록(줄별 거부 가능), Open Assumptions(사람이 거부하고 싶을 가능성 순). 보고서에는 **실행 수치**를 명시한다: 완료 티켓 수, 부상한 C4 결정 수, 3회 실패 중단 수, 제안된 침전물 줄 수.

### 컨텍스트 위생

- Phase 1~3은 한 컨텍스트에서, 경계에서만 압축한다.
- **디스크가 1차 소스, 대화 기억은 2차**: 경계를 넘었으면 디스크에서 아티팩트를 다시 읽고 기억으로 진행하지 않는다.
- Phase 4는 티켓마다 fresh 컨텍스트(서브에이전트)에서 실행된다.
- 핸드오프는 포인터만 전달한다(내용 복사 금지): 포인터(자료·결정 위치) + 다음 감시(다음 단계와 호출할 스킬) + 경고선(이미 기각된 방향).

## Output Contract

- C1~C5 각 체크포인트: 결정 요청은 질문+권장안+영향 범위를 명시하고, 승인 없이 다음 단계로 넘어가지 않는다.
- 완료 보고서: 출시 범위, 검증 증거, 페이퍼 트레일 위치, 야드 드리프트 findings, 침전물 목록(줄별 거부 가능), Open Assumptions 순위.
- 완료 정의: 모든 티켓이 증거와 함께 종료, 전체 변경 verify 통과, 페이퍼 트레일 정합, 보고서 발행 — 그리고 에이전트가 대신 내린 모든 결정이 "어디에 기록됐는지" 포인터 하나로 답 가능.

## Operating Rules

- 원본의 Claude Code 메커니즘 치환: Task tool 팀 오케스트레이션 → `subagent.spawn` 병렬 실행; tmux → 사용하지 않음.
- 원본이 참조하는 스킬은 이 환경에 전부 이식되어 있다: `drydock`(야드 감사), `ask-navigator`(포그 내비게이션), `harbor`(브리프 인계), `loft`(시각 아티팩트), `hud`(상태 표시), `intent`, `minimal-code-discipline` — 해당 Phase에서 직접 호출.
- Launch는 런타임 상태 머신을 소유하지 않는다. 모든 영속 주장은 디스크의 파일에 대한 것이며, 숨은 런타임에 대한 것이 아니다.
- 중단 후 재개: 아티팩트를 보존하고 중단한다. 이후 명시적 Launch 호출로만 계속하며, 사람의 승인을 추론하거나 `in_progress` 작업을 재생하지 않는다.
- 외부 모델(Codex/Gemini 등) 사용 옵션은 이 환경에서 불가 — Operating Rules에 명시하고 대체 없이 안내한다.
- hooks 연동(원본의 stop hook 등)은 이 환경에 없으므로 생략한다. 중단은 `cancel` 스킬을 사용한다.
