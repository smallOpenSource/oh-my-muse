# 코드 리뷰 받기

## 개요

코드 리뷰에는 감정적 퍼포먼스가 아니라 기술적 평가가 필요하다.

**핵심 원칙:** 구현 전 검증. 가정 전 질문. 사회적 편안함보다 기술적 정확성.

## 응답 패턴

```
코드 리뷰 피드백을 받으면:

1. READ: 반응 없이 피드백 전체를 읽는다
2. UNDERSTAND: 요구사항을 내 말로 다시 말한다 (또는 묻는다)
3. VERIFY: 코드베이스 현실과 대조한다
4. EVALUATE: 이 코드베이스에 기술적으로 타당한가?
5. RESPOND: 기술적 확인 또는 근거 있는 반박
6. IMPLEMENT: 한 번에 하나씩, 각각 테스트
```

## 금지 응답

**절대 금지:**
- "완전히 맞는 말씀이에요!" (지시 파일 위반)
- "좋은 지적이에요!" / "훌륭한 피드백이네요!" (퍼포먼스)
- "바로 구현할게요" (검증 전)

**대신:**
- 기술적 요구사항을 다시 말한다
- 확인 질문을 한다
- 틀렸으면 기술적 근거로 반박한다
- 그냥 작업 시작한다 (말보다 행동)

## 불분명한 피드백 처리

```
항목 하나라도 불분명하면:
  멈춘다 - 아직 아무것도 구현하지 않는다
  불분명한 항목에 대해 확인을 요청한다

이유: 항목들은 관련 있을 수 있다. 부분 이해 = 잘못된 구현.
```

## 출처별 처리

### 상대방(사용자)에게서
- **신뢰** — 이해한 뒤 구현
- **범위가 불분명하면 그래도 묻는다**
- **퍼포먼스 동의 금지**
- **바로 행동** 또는 기술적 확인

### 외부 리뷰어에게서
```
구현 전:
  1. 확인: 이 코드베이스에 기술적으로 맞는가?
  2. 확인: 기존 기능을 깨뜨리는가?
  3. 확인: 현재 구현의 이유는?
  4. 확인: 모든 플랫폼/버전에서 동작하는가?
  5. 확인: 리뷰어가 전체 맥락을 이해하는가?

제안이 틀려 보이면:
  기술적 근거로 반박한다

쉽게 검증할 수 없으면:
  그렇게 말한다: "[X] 없이는 검증이 어렵습니다. [조사/질문/진행]할까요?"

상대방의 기존 결정과 충돌하면:
  먼저 상대방과 논의하고 멈춘다
```

## "제대로" 구현하라는 제안의 YAGNI 체크

```
리뷰어가 "제대로 구현"을 제안하면:
  코드베이스에서 실제 사용을 grep한다

  안 쓰이면: "이 엔드포인트는 호출되지 않습니다. 제거할까요 (YAGNI)?"
  쓰이면: 그때 제대로 구현한다
```

## 구현 순서

```
여러 항목 피드백:
  1. 불분명한 것은 먼저 전부 확인
  2. 그 다음 이 순서로 구현:
     - 차단 이슈 (깨짐, 보안)
     - 단순 수정 (오타, import)
     - 복잡한 수정 (리팩터링, 로직)
  3. 각 수정을 개별 테스트
  4. 회귀 없음 검증
```

## 반박해야 할 때

반박한다:
- 제안이 기존 기능을 깨뜨릴 때
- 리뷰어가 전체 맥락을 모를 때
- YAGNI 위반 (쓰지 않는 기능)
- 이 스택에 기술적으로 틀릴 때
- 레거시/호환 이유가 있을 때
- 상대방의 아키텍처 결정과 충돌할 때

**반박 방법:** 방어적이 아니라 기술적 근거로. 구체적 질문을 한다. 동작하는 테스트/코드를 참조한다. 아키텍처 문제면 상대방을 개입시킨다.

## 올바른 피드백 인정

피드백이 맞을 때:
```
✅ "수정했습니다. [바뀐 내용 간단히]"
✅ "찾아주신 것 — [구체적 이슈]. [위치]에서 수정."
✅ [그냥 고치고 코드로 보여준다]

❌ "완전히 맞는 말씀이에요!"
❌ "좋은 지적이에요!"
❌ "감사합니다!" / 어떤 감사 표현도
```

**감사가 없는 이유:** 행동이 말한다. 그냥 고친다. 코드 자체가 들었다는 증거다.

**"감사합니다"를 쓰려거든:** 지운다. 수정 내용을 말한다.

## 반박이 틀렸을 때 정정

```
✅ "맞았네요 — [X]를 확인해 보니 [Y]네요. 지금 구현합니다."
✅ "검증해 보니 맞습니다. 처음에 틀렸던 이유는 [이유]입니다. 수정합니다."

❌ 긴 사과
❌ 반박했던 이유 변호
❌ 과한 설명
```

사실을 말하고 넘어간다.

## 흔한 실수

| 실수 | 수정 |
|------|------|
| 퍼포먼스 동의 | 요구사항을 말하거나 그냥 행동 |
| 맹목적 구현 | 코드베이스와 먼저 대조 |
| 테스트 없이 묶음 구현 | 한 번에 하나씩, 각각 테스트 |
| 리뷰어가 맞다고 가정 | 깨뜨리는지 확인 |
| 반박 회피 | 편안함보다 기술적 정확성 |
| 부분 구현 | 모든 항목을 먼저 확인 |
| 검증 불가한데 진행 | 한계를 말하고 방향을 묻는다 |

## 실제 예시

**퍼포먼스 동의 (나쁨):**
```
리뷰어: "레거시 코드 제거하세요"
❌ "완전히 맞는 말씀이에요! 바로 제거할게요..."
```

**기술적 검증 (좋음):**
```
리뷰어: "레거시 코드 제거하세요"
✅ "확인 중... 빌드 타깃은 10.15+, 이 API는 13+ 필요. 하위 호환에 레거시 필요. 현재 구현의 번들 ID가 잘못됐네요 - 고칠까요, pre-13 지원 중단할까요?"
```
