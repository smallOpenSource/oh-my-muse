# 스킬 작성

## 개요

**스킬 작성은 프로세스 문서에 적용한 테스트 주도 개발이다.**

**스킬 저장 위치:** `~/workspace/skills/` — 스킬 하나당 디렉토리 하나. 공식 작성
가이드 보충 자료는 `anthropic-best-practices.md` 참조.

테스트 케이스를 쓰고(서브에이전트 압박 시나리오), 실패를 보고(스킬 없는 기준
행동), 스킬을 쓰고(문서), 통과를 보고(에이전트가 준수), 리팩터한다(허점을 닫는다).

**핵심 원칙:** 스킬 없이 에이전트가 실패하는 것을 보지 않았으면, 그 스킬이
올바른 것을 가르치는지 모른다.

**필수 배경:** test-driven-development 스킬을 이해해야 한다. 그 스킬이 근본인
RED-GREEN-REFACTOR 사이클을 정의한다. 이 스킬은 TDD를 문서에 적용한다.

## 스킬이란?

**스킬**은 검증된 기법·패턴·도구의 참조 가이드다. 미래 에이전트가 효과적인
접근을 찾아 적용하게 돕는다.

**스킬은:** 재사용 가능한 기법, 패턴, 도구, 참조 가이드

**스킬이 아니다:** 문제를 한 번 해결한 이야기의 서사

## TDD 매핑

| TDD 개념 | 스킬 생성 |
|----------|----------|
| **테스트 케이스** | 서브에이전트 압박 시나리오 |
| **프로덕션 코드** | 스킬 문서 (SKILL.md) |
| **테스트 실패 (RED)** | 스킬 없이 에이전트가 규칙 위반 (기준) |
| **테스트 통과 (GREEN)** | 스킬 있으면 에이전트가 준수 |
| **리팩터** | 허점을 닫으면서 준수 유지 |
| **테스트 먼저 쓰기** | 스킬 쓰기 전에 기준 시나리오 실행 |
| **실패 보기** | 에이전트가 쓰는 합리화를 그대로 기록 |
| **최소 코드** | 그 위반만 다루는 스킬 작성 |
| **통과 보기** | 에이전트가 이제 준수하는지 검증 |
| **리팩터 사이클** | 새 합리화 찾기 → 막기 → 재검증 |

스킬 생성 전 과정이 RED-GREEN-REFACTOR를 따른다.

**[환경 한계]** 이 환경에서는 서브에이전트를 직접 파견할 수 없으므로, 압박
시나리오 실행은 상위 에이전트에게 위임 요청한다 (시나리오와 평가 기준을 보고서에
담아 전달).

## 스킬을 만들 때

**만든다:**
- 직관적으로 자명하지 않았던 기법
- 프로젝트를 넘나들며 다시 참조할 것
- 넓게 적용되는 패턴 (프로젝트 전용 아님)
- 남에게도 도움 되는 것

**만들지 않는다:**
- 일회성 해결
- 다른 곳에 잘 문서화된 표준 관행
- 프로젝트 전용 관례 (지시 파일에)
- 기계적 제약 (regex/검증으로 강제 가능하면 자동화 — 판단이 필요한 것에 문서를 쓴다)

## 스킬 타입

### 기법 (Technique)
따라 할 단계가 있는 구체적 방법

### 패턴 (Pattern)
문제에 대한 사고 방식

### 레퍼런스 (Reference)
API 문서, 문법 가이드, 도구 문서

## 디렉토리 구조

```
skills/
  skill-name/
    SKILL.md              # 메인 레퍼런스 (필수)
    supporting-file.*     # 필요할 때만
```

**플랫 네임스페이스** — 모든 스킬이 하나의 검색 가능한 네임스페이스에

**별도 파일로:**
1. **무거운 레퍼런스** (100줄 이상) - API 문서, 포괄적 문법
2. **재사용 도구** - 스크립트, 유틸리티, 템플릿

**인라인 유지:**
- 원칙과 개념
- 코드 패턴 (50줄 미만)
- 그 외 전부

## SKILL.md 구조

**Frontmatter (YAML):**
- 필수 필드 둘: `name`, `description` (전체 지원 필드는 [agentskills.io/specification](https://agentskills.io/specification))
- 총 1024자 이내
- `name`: 영문자·숫자·하이픈만
- `description`: 3인칭, 사용 시점만 기술 (무엇을 하는지 요약 금지)
  - "사용 시..."로 시작해 트리거 조건에 집중
  - 구체적 증상·상황·맥락 포함
  - **스킬의 절차·워크플로를 요약하지 않는다** (아래 SDO 참조)
  - 가능하면 500자 이내

```markdown
---
name: Skill-Name-With-Hyphens
description: "[구체적 트리거 조건과 증상]일 때 사용"
---

# 스킬 이름

## 개요
무엇인가? 1-2문장의 핵심 원칙.

## 사용 시점
[판단이 자명하지 않은 결정이면 작은 인라인 플로차트]

증상과 사용 케이스 불릿 목록
사용하지 않을 때

## 핵심 패턴 (기법/패턴용)
전/후 코드 비교

## 빠른 참조
자주 쓰는 작업을 스캔하는 표·불릿

## 구현
단순 패턴은 인라인 코드
무거운 레퍼런스·재사용 도구는 파일 링크

## 흔한 실수
무엇이 잘못되는가 + 수정

## 실제 영향 (선택)
구체적 결과
```

## 스킬 발견 최적화 (SDO)

**핵심:** 미래 에이전트가 스킬을 찾아야 한다.

### 1. 풍부한 description 필드

에이전트는 description을 읽고 지금 이 스킬을 읽을지 결정한다. 답해야 할 질문:
"지금 이 스킬을 읽어야 하는가?"

**형식:** "사용 시..."로 시작해 트리거 조건에만 집중.

**중요: description = 사용 시점, 스킬이 하는 일이 아니다.**

description이 스킬의 워크플로를 요약하면, 에이전트가 description만 따르고 전체
스킬을 읽지 않을 수 있다. "태스크 사이에 코드 리뷰"라는 description 때문에
에이전트가 리뷰를 한 번만 했다 — 플로차트에는 두 번(스펙 준수 다음 코드 품질)이
명확했는데. description을 "독립적인 태스크로 된 구현 계획을 실행할 때 사용"으로
바꾸자(워크플로 요약 없음) 에이전트가 플로차트를 읽고 두 단계 리뷰를 따랐다.

**함정:** 워크플로를 요약한 description은 에이전트가 탈 지름길을 만든다. 스킬
본문은 건너뛰는 문서가 된다.

```yaml
# ❌ 나쁨: 워크플로 요약 - 에이전트가 스킬 대신 이것을 따를 수 있음
description: "계획을 실행할 때 사용 - 태스크마다 서브에이전트를 파견하고 태스크 사이 코드 리뷰"

# ✅ 좋음: 트리거 조건만, 워크플로 요약 없음
description: "이 세션에서 독립적인 태스크들로 된 구현 계획을 실행할 때 사용"
```

**내용:**
- 트리거·증상·상황을 구체적으로
- *문제*를 기술 (레이스 컨디션, 일관 없는 동작), 언어별 증상(setTimeout, sleep)이 아님
- 기술에 구애받지 않게 — 스킬 자체가 기술 전용이면 그걸 명시
- 3인칭
- **스킬의 절차·워크플로를 요약하지 않는다**

### 2. 키워드 커버리지

에이전트가 검색할 단어를 쓴다: 에러 메시지, 증상("flaky", "hanging", "zombie"),
동의어("timeout/hang/freeze"), 실제 명령·라이브러리·파일 타입.

### 3. 서술적 네이밍

**능동태, 동사 우선:** `creating-skills` O, `skill-creation` X. 과정에는
-ing형이 잘 통한다: `creating-skills`, `testing-skills`, `debugging-with-logs`.

### 4. 토큰 효율 (중요)

자주 로드되는 스킬은 매 대화에 로드된다. 모든 토큰이 셈이다.

- 자주 로드되는 스킬: 총 200단어 이내 목표
- 그 외 스킬: 500단어 이내 (그래도 간결하게)

**기법:**
- 상세는 도구 help로: "search-conversations는 여러 모드와 필터를 지원한다. 상세는 --help."
- 크로스 레퍼런스: 반복하지 말고 다른 스킬을 가리킨다
- 예시 압축: 42단어 예시를 20단어로
- 중복 제거: 크로스 레퍼런스된 스킬의 내용을 반복하지 않는다

**이 환경의 스킬 발견:** 스킬 description은 한국어로 쓰되, 에이전트가 검색할
영문 기술 토큰(에러 메시지·명령어·파일명)도 본문 앞부분에 함께 둔다.

### 5. 다른 스킬 크로스 레퍼런스

스킬 이름만 쓰고 명시적 요구 마커를 붙인다:
- ✅ 좋음: `**필수 하위 스킬:** subagent-driven-development 스킬 사용`
- ❌ 나쁨: `@skills/...` (즉시 강제 로드, 컨텍스트 소모)

## 플로차트 사용

**플로차트는 오직:**
- 자명하지 않은 결정 지점
- 너무 일찍 멈출 수 있는 절차 루프
- "A vs B 언제" 결정

**플로차트 금지:**
- 레퍼런스 자료 → 표, 목록
- 코드 예시 → 마크다운 블록
- 선형 지시 → 번호 목록
- 의미 없는 라벨 (step1, helper2)

이 디렉토리의 `graphviz-conventions.dot`에 graphviz 스타일 규칙이 있다.
`render-graphs.js`로 스킬의 플로차트를 SVG로 렌더할 수 있다:
```bash
node ./render-graphs.js ../some-skill
```

## 코드 예시

**평범한 여러 개보다 훌륭한 하나.**

- 완전하고 실행 가능하게
- 왜 그런지 설명하는 주석
- 실제 시나리오에서
- 패턴을 명확히 보여주고
- 적용 준비된 형태 (빈칸 채우기 템플릿 아님)

**하지 말 것:** 5개 이상 언어로 구현, 채우기식 템플릿, 꾸며낸 예시.

## 철칙 (TDD와 동일)

```
실패하는 테스트 없이 스킬 금지
```

새 스킬과 기존 스킬 수정에 모두 적용된다. 테스트 없이 스킬을 쓰면? 지운다.
처음부터. 테스트 없이 스킬을 수정하면? 같은 위반.

**예외 없음:** "단순 추가"도, "섹션 하나 추가"도, "문서 업데이트"도 아니다.

## 스킬 타입별 테스트

### 규율 강제 스킬 (규칙/요구사항)

**예:** TDD, verification-before-completion

**테스트:** 학문적 질문(이해하는가?) → 압박 시나리오(스트레스에서 준수하는가?) →
복합 압박(시간 + 매몰 비용 + 피로). 합리화를 파악하고 명시적 카운터를 추가한다.

**성공 기준:** 최대 압박에서 에이전트가 규칙을 따른다.

### 기법 스킬 (how-to)

**테스트:** 적용 시나리오(새 시나리오에 올바르게 적용하는가?), 변형(엣지 케이스),
정보 누락(지시에 빈틈이 있는가?).

**성공 기준:** 새 시나리오에 기법을 성공적으로 적용한다.

### 패턴 스킬 (사고 모델)

**테스트:** 인식(패턴이 적용될 때 알아보는가?), 적용, 반례(적용하지 말아야 할
때를 아는가?).

### 레퍼런스 스킬 (문서/API)

**테스트:** 검색(올바른 정보를 찾는가?), 적용, 빈틈(흔한 사용 케이스가 커버되는가?).

## 워딩 마이크로 테스트

전체 압박 시나리오는 느리고 비싸다. 워딩 자체를 먼저 검증한다:

1. **호출당 새 컨텍스트 샘플 하나** — 시스템 프롬프트 = 안내가 실제 살 맥락(전체 스킬)
2. **항상 no-guidance 대조군 포함.** 대조군이 실패를 보이지 않으면 고칠 게 없다 — 멈춘다.
3. **변형당 5회 이상.** 단일 샘플은 거짓말한다.
4. **플래그된 매치를 전부 직접 읽는다.** 템플릿 메아리와 인용된 반례가 적중으로 위장한다.
5. **분산도 지표다.** 안내가 통하면 반복이 같은 모양으로 수렴한다. 5회 반복이 5가지 해석이면 워딩이 구속하지 않는 것이다 — 말을 늘리기 전에 형태를 조인다.

## 실패에 형태를 맞춘다

안내를 쓰기 전에 기준 실패를 분류한다. 한 실패 타입을 막는 형태가 다른 타입에는
측정 가능하게 역효과다.

| 기준 실패 | 맞는 형태 | 틀린 형태 |
|---|---|---|
| 압박에서 규칙을 건너뛴다 (알면서 안 지킨다) | 금지 + 합리화 표 + 경고 신호 | 부드러운 안내 ("선호한다", "고려한다") |
| 준수하지만 출력 모양이 틀렸다 | 긍정적 레시피·계약: 출력이 무엇인지 — 부분, 순서 | 금지 목록 |
| 이미 만드는 것에 필수 요소 누락 | 구조적: 템플릿의 필수 필드·슬롯 | 템플릿 옆 산문 리마인더 |
| 조건에 따라 달라져야 하는 동작 | 관찰 가능한 조건에 묶인 조건문 | 무조건 규칙 + 예외 조항 |

**형태 규칙:**
- **뉘앙스 조항 금지.** "중요하지 않으면 X 금지"는 협상을 다시 연다.
- **면제 조항은 범위를 정하지 않는다.** 출력의 일부가 면제돼야 하면 규칙이 닿지 않게 구조를 바꾼다.

## 합리화 방어 (Bulletproofing)

규율을 강제하는 스킬용 툴킷이다 — 규칙을 알면서 압박에 건너뛰는 에이전트 대상.

- **모든 허점을 명시적으로 닫는다:** 규칙만 말하지 말고 특정 우회를 금지한다.
- **"정신 대 문자" 논증을 차단한다:** 초반에 기초 원칙을 둔다 — "규칙의 문자를 어기는 것은 정신을 어기는 것이다."
- **합리화 표를 만든다:** 기준 테스트에서 에이전트가 한 모든 변명을 표에 담는다.
- **경고 신호 목록을 만든다:** 합리화 중인지 스스로 점검하기 쉽게.

심리학 배경은 `persuasion-principles.md` 참조.

## 안티 패턴

### ❌ 서사 예시
"2025-10-03 세션에서 empty projectDir이..."
**이유:** 너무 구체적, 재사용 불가

### ❌ 다언어 희석
example-js.js, example-py.py, example-go.go
**이유:** 평범한 품질, 유지보수 부담

### ❌ 플로차트에 코드
**이유:** 복사-붙여넣기 불가, 읽기 어렵다

### ❌ 일반 라벨
helper1, helper2, step3, pattern4
**이유:** 라벨은 의미가 있어야 한다

## 멈춤: 다음 스킬 전

**스킬을 하나라도 쓴 뒤에는 반드시 멈추고 배포 절차를 끝낸다.**

**하지 말 것:**
- 각각 테스트 없이 여러 스킬을 묶음으로 만들기
- 현재 것이 검증되기 전에 다음 스킬로 이동
- "묶음이 효율적"이라 테스트 건너뛰기

## 스킬 생성 체크리스트 (TDD 적용)

**중요: 아래 각 항목에 todo를 만든다.**

**RED - 실패하는 테스트 쓰기:**
- [ ] 압박 시나리오 만들기 (규율 스킬은 3개 이상 복합 압박)
- [ ] 스킬 없이 시나리오 실행 — 기준 행동을 그대로 기록
- [ ] 합리화/실패의 패턴 파악

**GREEN - 최소 스킬 쓰기:**
- [ ] 이름은 영문자·숫자·하이픈만
- [ ] 필수 `name`·`description` YAML frontmatter (총 1024자 이내)
- [ ] description은 "사용 시..."로 시작, 구체적 트리거/증상
- [ ] description은 3인칭
- [ ] 검색용 키워드를 곳곳에 (에러, 증상, 도구)
- [ ] 명확한 개요와 핵심 원칙
- [ ] RED에서 파악한 구체적 기준 실패를 다룬다
- [ ] 안내 형태가 실패 타입에 맞는다 (위 표 참조)
- [ ] 코드 인라인 또는 별도 파일 링크
- [ ] 훌륭한 예시 하나 (다언어 아님)
- [ ] 스킬 있는 시나리오 실행 — 에이전트가 이제 준수하는지 검증

**REFACTOR - 허점 닫기:**
- [ ] 테스트에서 새 합리화 파악
- [ ] 명시적 카운터 추가 (규율 스킬이면)
- [ ] 모든 테스트 반복에서 합리화 표 만들기
- [ ] 경고 신호 목록 만들기
- [ ] 막힐 때까지 재테스트

**품질 검사:**
- [ ] 판단이 자명하지 않을 때만 작은 플로차트
- [ ] 빠른 참조 표
- [ ] 흔한 실수 섹션
- [ ] 서사 스토리텔링 없음
- [ ] 보조 파일은 도구·무거운 레퍼런스만

**배포:**
- [ ] 스킬을 git에 커밋
- [ ] 넓게 유용하면 upstream에 PR 고려
