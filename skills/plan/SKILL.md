## Purpose

요구사항을 이해하지 않고 코드부터 짜면 재작업과 범위 크립이 생긴다. 이 스킬은 요청의 구체도에 따라 인터뷰 모드(모호한 요청)와 다이렉트 모드(상세한 요청)를 자동 감지하고, 합의 모드(Planner→Architect→Critic 루프)와 리뷰 모드(기존 계획 평가)를 지원한다.

## Workflow

### 모드 선택

- **인터뷰 모드** (기본, 모호한 요청): 요구사항을 하나씩 질문하며 수집한다. 코드베이스 사실은 물어보기 전에 먼저 서브에이전트로 찾아내고, 그 다음 정보가 있는 후속 질문을 한다.
- **다이렉트 모드** (`--direct`, 상세한 요청): 인터뷰 없이 바로 계획을 만든다.
- **합의 모드** (`--consensus` / ralplan): Planner 초안 → Architect 검토 → Critic 평가 루프를 Critic 승인까지 반복(최대 5회). 최종 계획에는 ADR(결정/동인/대안/선택 이유/결과/후속)을 포함한다. 고위험 작업은 `--deliberate`로 프리모템 3개 + 확장 테스트 계획(단위/통합/e2e/관측)을 추가한다.
- **리뷰 모드** (`--review`): 기존 계획 파일을 Critic 관점으로 평가해 APPROVED/REVISE/REJECT 판정을 낸다.

### 계획서 형식

- 요구사항 요약, 수락 기준(테스트 가능), 구현 단계(파일 참조 포함), 위험과 완화책, 검증 단계를 포함한다.
- 합의 모드 최종 출력에는 RALPLAN-DR 요약(원칙, 결정 동인, 대안)과 ADR 섹션을 포함한다.
- 계획서는 `~/workspace/.omc/plans/`에 저장한다. 승인 전까지 상태는 `pending approval`.

## Output Contract

- 산출물: `~/workspace/.omc/plans/`의 계획서, 수락 기준, (합의 모드) ADR, (리뷰 모드) 판정과 피드백.
- 계획/실행 경계: 명시적 실행 승인 전까지는 소스 수정·커밋·PR·실행 스킬 호출·구현 위임을 하지 않는다.
- 인터뷰에서는 한 번에 하나의 질문만 한다.
- **디자인 옵션 제시**: 선택지를 한꺼번에 나열하지 않는다. 개요 2-3문장 → 옵션 A(트레이드오프 포함) → 사용자 반응 → 옵션 B(트레이드오프 포함) → 사용자 반응 → 마지막에 추천. 추천은 옵션 논의가 끝난 뒤에만 낸다.

## 중지·에스컬레이션 조건

- 요구사항이 계획 세우기에 충분하면 인터뷰를 멈춘다. 과도한 추가 질문 금지.
- 합의 모드 5회 반복에 합의가 안 되면 최선의 버전을 사용자에게 보여주고 "전문가 합의 미도달"을 명시한다.
- 사용자가 실행 경로를 지정하지 않고 "그냥 해"라고 하면 현재 계획서를 `pending approval`로 출력하고 구조화된 승인 UI로 명시적 실행 승인을 받는다. 승인 전까지 실행 스킬 호출·파일 수정·위임을 하지 않는다.
- 비즈니스 판단이 필요한 상충 트레이드오프는 사용자에게 에스컬레이션한다.

## 최종 점검

- [ ] 수락 기준의 90% 이상이 테스트 가능(구체 수치 포함 — "빠르게" → "p99 < 200ms")
- [ ] 주장의 80% 이상이 파일/라인 인용
- [ ] 모든 위험에 완화책 존재
- [ ] 계획서가 `~/workspace/.omc/plans/`에 저장됨
- [ ] 합의 모드: RALPLAN-DR 요약(원칙 3-5개, 동인 상위 3개, 대안 2개 이상 또는 무효화 근거) 포함
- [ ] 합의 모드 최종: ADR 섹션(결정/동인/대안/선택 이유/결과/후속) 포함
- [ ] deliberate 모드: 프리모템 3개 + 확장 테스트 계획(단위/통합/e2e/관측) 포함

## Operating Rules

- **질문 분류**: 코드베이스 사실(패턴·위치)은 서브에이전트로 먼저 조사하고 사용자에게 묻지 않는다. 사용자 선호·범위 결정·요구사항만 질문한다. 질문은 `muse.create_options`로 클릭 선택형으로 낸다.
- **합의 모드 순차 실행**: Architect와 Critic 리뷰는 같은 고정 계획 스냅샷을 각각 독립적으로 본다. 같은 병렬 배치에 넣지 말고, Architect 완료 후 Critic을 별도 `subagent.spawn` 호출로 실행한다. 결과 합성은 Planner 단계에서만 한다.
- **외부 모델 불가**: 원문의 `--architect codex` / `--critic codex` 옵션(Codex CLI 교체)은 이 환경에서 동작하지 않는다. 내부 서브에이전트로 대체하고, 불가함을 짧게 알린다.
- **hooks 대체**: 원문의 Stop hook 강제 지속(`ralplan-state.json`, `state_write`/`state_clear`)은 이 환경에 없으므로, 합의 루프는 Workflow 단계로 명시적으로 수행한다. 필요 시 내 `hooks`를 대체 수단으로 사용한다.
- **경로 치환**: 원문의 `.omc/plans/`, `.claude/omc.jsonc`는 `~/workspace/` 기준으로 읽고 쓴다.
- **병렬 실행**: 원문의 `Task(subagent_type=...)` 표기는 전부 `subagent.spawn`으로 치환한다. tmux/`omc team` 런타임은 적용하지 않는다.
- **품질 기준**: 계획서의 주장은 파일/라인 인용 80% 이상, 수락 기준은 90% 이상 테스트 가능해야 한다.
