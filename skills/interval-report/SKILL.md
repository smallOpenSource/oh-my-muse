# interval-report: 장기 수행 중간 보고 (docs/intermission.md)

## Purpose

장기 수행은 사람에게 보이지 않는다. 사용자는 지시를 넣고 나면 지금 어디쯤인지, 언제 끝나는지, 그동안 무슨 일이 있었는지 알 방법이 없다. 이 스킬은 그 공백을 `docs/intermission.md` 파일 하나로 메우고, **계획된 작업이 끝날 때까지 그 파일을 갱신**한다. 읽는 사람이 전체 trajectory를 한 번에 파악할 수 있어야 한다. 그게 이 파일의 유일한 존재 이유다.

여기서 오작동의 대가는 느린 진행이 아니라 **거짓 보고**다. 시각을 추측하면 elapsed가 허구가 되고, 자신감 있는 단일 숫자 ETA를 뱉으면 사용자가 그걸 믿고 계획을 세운다. 그래서 실측 규칙과 ETA 정직성 규칙은 보고의 매끄러움보다 우선한다. 답변은 한글(기술 토큰·경로·명령은 영문).

**쓴다:** 사용자 지시 하나가 여러 단계·긴 시간으로 늘어나 중간에 사람이 상태를 볼 수 없는 수행. 자리를 비운 사용자가 돌아와 그동안의 trajectory를 한 번에 파악해야 할 때. 진행 중 사용자가 알아야 할 일이 생겼는데(가정이 깨짐, 외부 대기, 예상 밖 발견) 지금 당장 물을 만큼은 아닐 때. 사용자가 "interval-report"/"중간 보고"/"진행 상황 보고"/"intermission"이라고 할 때.

**쓰지 않는다:** **단발 작업** — 한 번에 끝나는 일에 보고 파일을 세우면 파일 관리가 작업보다 비싸다. **상태의 원본 저장소로** — 이 스킬은 렌더러지 원장이 아니다. 진행 상태의 원본이 필요하면 목표/원장(goal)을 쓴다. **컨텍스트 임계 감지·자동 발화** — 스스로 발화하려 들지 마라. 자가 트리거는 설치하지 않는다. **compaction 직전 준비** — 그건 `ready-compact`다(독자: 다음 세션의 에이전트. 이 스킬의 독자는 사람). 이름이 비슷해 헷갈리지만 하는 일이 다르다. 둘은 같은 세션에서 공존한다 — 보고서가 있다고 resume 프롬프트를 생략하지 말고, 그 반대도 마찬가지다.

## Workflow

### 0. READ-BACK (추정 금지)

언제나 여기서 시작한다. 파일이 있는지, 시작 시각이 무엇인지 **읽어서** 확인한다. 기억에 의존하지 마라.

> **파일에 이미 시작 시각이 있으면 절대 덮어쓰지 않는다.**

```bash
F=docs/intermission.md
if [ -f "$F" ] && grep -q '^started_epoch:' "$F"; then
  START=$(grep -m1 '^started_epoch:' "$F" | tr -cd '0-9')   # 파일이 정본
else
  START=$(date +%s)                                          # 최초 1회만
fi
NOW=$(date +%s)
ELAPSED=$(( NOW - START ))
printf 'start=%s elapsed=%dh %02dm\n' "$START" $(( ELAPSED / 3600 )) $(( ELAPSED % 3600 / 60 ))
```

- **왜 영속이 필수인가:** compaction·resume 후에는 모델이 시작 시각을 기억하지 못한다. 그때 `now`로 재스탬프하면 elapsed가 0으로 붕괴한다. 붕괴는 조용하고, 하필 **긴 작업일수록 잘 일어난다**. 이 규칙은 편의보다 우선한다.
- **정수 산술만 쓴다.** `date -d @...`(GNU)와 `date -v`(BSD)는 문법이 갈린다. `date +%s`로 epoch만 얻고 뺄셈은 셸에 맡기면 분기가 사라진다.
- **사람이 읽는 표기도 같이 영속한다.** epoch만 두면 파일을 연 사람이 값을 검증할 수 없다.

측정 대상은 세션 전체가 아니라 **마지막 사용자 지시로 시작된 현재 수행분**이다(시작 시각 = 마지막으로 사용자가 대화·지시한 시점). 새 지시면 시작 시각을 새로 찍고 보고서를 새로 연다. 승인·답변("응", "1번으로")은 수행분을 잇는다. 애매하면 옮기지 않는 쪽(낙관 편향이 더 나쁘다).

### 1. 자리 잡기 (docs/ + .gitignore, 최초 1회)

산출물은 타깃 repo의 `docs/intermission.md`다. `docs/`가 없으면 만든다.

이건 **세션 로컬 작업물**이지 그 프로젝트의 문서가 아니다. 커밋되면 우리 세션의 진행 상황이 남의 repo 히스토리에 영구히 남는다. 그래서 `.gitignore`에 멱등하게 한 줄 추가한다:

```
# interval-report: session-local progress report (not project documentation)
docs/intermission.md
```

- **`.gitignore`는 그 프로젝트의 파일이다.** 무엇을 왜 추가하는지 한 줄로 **사용자에게 알리고** 진행한다(승인을 기다리며 멈추라는 게 아니라, 사용자가 모르는 채로 남의 repo가 바뀌는 일을 막으라는 것이다).
- 이미 무시되고 있으면(`git check-ignore -q docs/intermission.md`) 추가하지 않는다. git repo가 아니면 이 단계를 건너뛴다.
- 사용자가 보고서를 커밋 대상으로 원한다고 명시하면 추가하지 않고 그대로 둔다.

### 2. 보고서 렌더

필수 항목 8개는 **전부** 있어야 한다: 시작 시간 / 현재 상태 / elapsed / 예상 잔여 / 예상 종료 / 진행·잔여 작업 표 / 발생 이벤트 / 인지 중인 constraints.

**작업 표는 하나다.** 상태 값은 `완료`·`진행중`·`대기` 3종뿐이다.

```markdown
---
started_epoch: 1784181572
started_human: "2026-07-16 14:59 KST"
updated_human: "2026-07-16 16:20 KST"
---

# 중간 보고: DB 마이그레이션 롤아웃

| 항목 | 값 |
|---|---|
| 시작 | 2026-07-16 14:59 KST |
| 현재 상태 | 3번(스테이징 검증) 진행 중. 4번부터 대기. |
| elapsed | 1h 21m |
| 예상 잔여 | 40m ~ 2h (확신: 낮음) |
| 예상 종료 | 17:00 ~ 18:20 KST |

**ETA 가정:** 남은 3건이 끝난 2건과 비슷한 크기다(확인된 바 없음). 5번이 사용자 승인 대기라 상한이 열려 있다.

## 작업

| # | 작업 | 상태 |
|---|---|---|
| 1 | 스키마 diff 추출 | 완료 |
| 2 | 마이그레이션 스크립트 작성 | 완료 |
| 3 | 스테이징 검증 | 진행중 |
| 4 | 롤백 절차 문서화 | 대기 |
| 5 | 운영 반영 | 대기 |

## 발생 이벤트
- 15:34 스테이징 시드가 3개월 낡아 일부 검증을 건너뜀. 사용자 판단이 필요할 수 있음.
- 16:02 `npm i`가 프록시 뒤에서 2회 실패. 재시도로 통과. 조치 불필요.

## 인지 중인 constraints
- 운영 반영은 사용자 승인 후에만(전역 규칙).
- 스테이징 DB는 18:00에 야간 배치가 잡아간다. 3번을 그 전에 끝내야 한다.
- 롤백 절차는 아직 검증되지 않았다. 5번의 전제 조건이다.
```

- **발생 이벤트**는 사용자가 알아야 할 것만 적는다. 기준은 "이걸 몰랐다면 사용자가 다르게 판단했을까". 가정이 깨진 사건은 반드시 남긴다.
- 항목에 쓸 내용이 없으면 항목을 지우지 말고 "없음"이라고 적는다.

### 3. 갱신 리듬

갱신은 **계획된 작업이 끝날 때까지** 이어진다. 시점은 사건이 정한다: 작업 표 항목 상태 변경 / 사용자가 알아야 할 이벤트 / constraints 변경 / ETA 가정 붕괴(**가장 중요** — 가정이 깨졌는데 ETA를 그대로 두면 그 순간부터 보고서는 거짓이다) / 사용자가 물었을 때.

매 갱신마다 0단계 READ-BACK을 먼저 한다. `updated_human`을 새로 찍고 `started_epoch`는 손대지 않는다. 갱신할 게 없으면 갱신하지 않는다(타임스탬프만 바꾸는 것은 잡음이다).

### 4. 검증 (보고 의무)

```bash
F=docs/intermission.md
grep -m1 '^started_epoch:' "$F"        # 0단계에서 읽은 값과 동일해야 한다
grep -m1 '^started_human:' "$F"
git check-ignore -q "$F" 2>/dev/null && echo "gitignore: ok" || echo "gitignore: 미적용 (git repo가 아니면 정상, 아니면 1단계 확인)"
```

체크리스트: `started_epoch`가 0단계 값과 같은가(다르면 재스탬프 사고, 즉시 복구) / elapsed가 직전 보고보다 커졌는가 / 필수 항목 8개 전부 있는가 / 작업 표가 하나인가, 상태가 3종뿐인가 / ETA가 범위+확신 라벨인가 / ETA 옆에 가정이 적혀 있고 유효한가 / 표의 상태가 실제 진행과 맞는가(**갱신하지 않은 보고서는 오래된 보고서가 아니라 틀린 보고서다**).

## Output Contract

사용자에게는 파일 경로와 함께 **지금 값**을 한 줄로 준다. 파일을 열게 하지 마라.

```
docs/intermission.md 갱신: elapsed 1h 21m, 2/5 완료, 예상 잔여 40m ~ 2h (확신: 낮음)
```

인자: `[--path <파일>] [--close] [지시 요약]`. `--path`는 산출 경로 변경(.gitignore 게이트 그대로 적용). `--close`는 마지막 갱신 후 보고서 닫기(전 항목 종료 상태로 맞추고 elapsed 확정, 예상 잔여·종료를 실제 값으로 대체). 인자 없이 파일이 이미 있으면 **갱신**이다. 언제나 READ-BACK이 먼저다.

## Operating Rules

- 시각의 출처는 `date` 하나다. 추측·역산 금지. `date +%s`(epoch 산술) + `date '+%Y-%m-%d %H:%M %Z'`(사람용 표기).
- 시작 시각은 파일이 정본이다. READ-BACK이 먼저, 계산은 그다음.
- ETA는 실측량(경과·완료·진행중·대기)에서만 유도하고, **범위 + 확신 라벨(높음/보통/낮음)**로 내고, 가정을 곁에 적는다. 단일 숫자 금지. 범위를 못 내겠으면 "모른다"고 적는다(허용된 답).
- 90% 천장: 9/10 지점에서 남은 노력이 가장 클 수 있다. 꼬리에서 선형 외삽을 믿지 말고, 카운트가 올라도 상한을 좁히지 마라.
- 이 스킬은 시간 레이어와 렌더러다. 원장도, 트리거도, resume 프롬프트도 아니다.
  - 상태의 원본이 필요하면 목표/원장(예: ultra-init 스킬의 ultragoal)을 읽어 렌더하되, **상태를 보고서에 복제하지 않는다**(어긋나면 원장이 맞다).
  - 자가 트리거·자동 발화는 설치하지 않는다(그 영역은 smart-compact). 주기적 갱신이 필요하면 내 cron/hooks로 스케줄할 수 있지만, 그건 이 스킬 호출과 별개로 사용자와 합의한다.
  - compaction 직전 resume 프롬프트는 ready-compact의 일이다(독자가 다르다: 사람 vs 다음 세션 에이전트).
- 산출물은 세션 로컬이다. 남의 repo에 남기지 않는다(`.gitignore` 게이트).
- 계획된 작업이 끝날 때까지 갱신한다. 끝나면 마지막 갱신으로 닫는다.

## 함정

- **now로 재스탬프**: 이 스킬에서 데이터가 거짓이 되는 유일하고 실재하는 경로. 파일에 시작 시각이 있으면 그게 정본이다.
- **세션 시작을 시작 시각으로 잡기 / 승인 한마디를 새 지시로 오인해 옮기기.**
- **자신감 있는 단일 숫자**: "정직한 ETA"를 표방하면서 이걸 하면 침묵보다 나쁘다.
- **꼬리 선형 외삽 / 표를 둘로 쪼개기 / 이벤트 절을 로그로 만들기 / 파일만 쓰고 검증 안 하기.**
- **`.gitignore` 정리 시도**(이 스킬은 한 줄 멱등 추가만), **남의 repo를 조용히 건드리기**, **`date` 계산 옵션 의존**(GNU/BSD 갈림).
