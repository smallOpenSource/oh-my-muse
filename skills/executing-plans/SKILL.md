# 계획 실행 (인라인)

계획을 이 세션에서 직접, 태스크 단위로 실행한다: 태스크별 구현자 서브에이전트
없음, 태스크별 리뷰어 없음. 마지막에 한 번의 새-컨텍스트 전체 브랜치 리뷰.

**핵심 원칙:** 계획이 이미 생각을 끝냈다. 정확히 실행하고, 실패를 봤다가 통과한
테스트로 각 단계를 증명하고, 내 망각을 견디는 기록을 남긴다.

**서술:** 도구 호출 사이에는 한 줄 이내로만 말한다 — 기록은 장부와 도구 결과가 맡는다.

**연속 실행:** 태스크 사이에 상대방에게 확인하지 않는다. 인라인 실행을 고른
이유는 비용을 아끼기 위해서다. 계획의 모든 태스크를 멈추지 않고 실행한다.

**판결, 정지 아님.** 충돌·모호함·계획 결함 — 판단한다. 스펙이 구속력 있는 권위고,
계획은 그 논증이며, 둘 다 답하지 않는 것은 내 판단이 정한다. 모든 결정은 장부에
`Ruling: <결정 내용> — <이유> — <틀렸을 때 비용>`으로 기록하고 계속 간다. 장부에
없는 계획 이탈은 몰래 내린 결정이다.

**멈추는 경우는 오직 네 가지:** 되돌릴 수 없거나 파괴적인 작업, 보안 민감 작업,
관례상 먼저 물어보는 워크트리 밖 부작용(머지·공유 브랜치 푸시·배포), 모든
전진 경로가 추측뿐인 깨진 계획. 그때는 멈추고 묻는다.

## 사용 시점

- writing-plans 스킬의 계획서가 있고 상대방이 인계 시점에 인라인 실행을 골랐다.
- 하네스에 서브에이전트 도구가 없다. 파견을 지어내지 말고 여기서 실행한다.
- 태스크가 대체로 독립적이다 — subagent-driven-development와 같은 전제조건.

## 준비

using-git-worktrees 스킬로 격리된 워크스페이스를 확보하거나 기존 것을 확인한다.
상대방의 명시적 동의 없이 main/master 브랜치에서 구현을 시작하지 않는다.

대화 메모리는 압축을 견디지 못한다. 장부 파일에 진행을 기록한다 — todo는 실시간
뷰이고, 장부가 기록이다.

- 각 계획은 워크스페이스를 소유한다: 시작 시 `../subagent-driven-development/scripts/sdd-workspace PLAN_FILE` 실행 — 계획의 git-ignored 디렉토리(`<repo-root>/.superpowers/sdd/<plan-basename>/`) 경로를 출력한다. 다른 계획의 디렉토리는 읽지도 쓰지도 않는다.
- `<workspace>/progress.md`에 이 계획의 장부가 있는지 확인한다. 첫 줄이 내 계획서 파일을 가리키면 `Task <N>: complete` 줄이 있는 태스크는 끝난 것이다 — 다시 하지 말고, 그 줄 없는 첫 태스크부터 재개한다.
- 장부 첫 줄: `# SDD ledger — plan: <plan file path>`.
- 계획서·스펙을 읽고 태스크마다 todo를 만든다.

**필수 하위 스킬:** 지금 test-driven-development 스킬을 로드한다. Task 1 전에.
아래 모든 태스크의 모든 단계를 지배한다.

Task 1 전에 계획서를 충돌 스캔한다: 인터페이스를 공유하는 태스크 쌍마다 한 행 —
두 태스크, 한쪽이 만드는 것과 다른 쪽이 쓰는 것, 발견 내용. 공유가 없으면
`Pre-flight: no shared interfaces` 한 줄. 각 충돌은 스펙을 구속 권위로 판결하고
장부에 기록한다.

## 태스크 루프

### 1. 태스크 가져오기

- 이 스킬의 `scripts/task-start PLAN_FILE N` 실행 — 브리프 경로와 BASE(태스크 리뷰 범위의 기준 커밋)를 한 번에 출력한다. 모든 태스크의 브리프를 읽는다: 기억은 요약이고 브리프에 정확한 값·시그니처·테스트 케이스가 있다.
- 태스크의 todo를 in_progress로 표시.

### 2. 단계 작업

계획서의 단계는 이미 RED-GREEN 순서다. 그 순서대로, 로드한 test-driven-development
아래에서 따른다. 테스트 단계의 코드는 먼저 쓰고 먼저 실행한다. 실패를 보는 것은
단계이지 형식이 아니다 — 구현 전에 통과하는 테스트는 테스트에 대한 발견이다.

명령을 실행하는 모든 단계에는 `Expected:` 줄이 있다. 명령을 실행하고 출력을 읽고
비교한다. 세 가지 결과:

- **일치.** 다음 단계.
- **코드가 틀렸다.** systematic-debugging 스킬 사용. 증상에 패치하지 말고 원인을 찾는다.
- **계획이 틀렸다** — 단계가 스펙과 모순되거나, 이전 태스크의 인터페이스가 이 태스크가 쓰는 것과 다르거나, 동작할 수 없는 명령. 스펙을 만족하는 최소 변경을 판결하고 장부에 `Task <N>: Ruling: <발견> — <결정과 이유>`로 기록하고 계속한다.

계획서의 커밋 단계대로 커밋한다.

### 3. 완료 계약

태스크의 장부 줄을 쓰기 전에 아래가 모두 참이어야 한다 — 이 세션의 증거로:

- 브리프가 지목한 모든 테스트가 이 태스크에서 존재하고 실행됐으며 출력을 읽었다.
- 태스크의 최종 테스트 실행이 통과했다 — `task-done`이 그 실행이며 명령과 결과를 장부 줄에 쓴다.
- 브리프의 모든 `Expected:` 줄을 실제 출력과 비교했다.
- 브리프의 모든 이탈에 `Ruling:` 줄이 장부에 있다.

**필수 하위 스킬:** verification-before-completion 스킬이 이 주장을 지배한다.
하나라도 빠지면 태스크는 미완이다: 끝낸다.

### 4. 태스크 완료

이 스킬의 `scripts/task-done PLAN_FILE N BASE -- <test command>` 실행 (테스트 명령은
브리프가 그 태스크 전체에 지목한 것). 테스트를 실행하고 전체 출력을 워크스페이스에
보관하고 꼬리를 출력하고 — 통과했을 때만 장부에 완료 줄을 추가한다:

`Task <N>: complete (commits <base7>..<head7>, tests: <command> → <result>)`

실패한 실행은 아무것도 기록하지 않는다. 태스크는 미완이다. 기록되면 todo를 완료
표시하고 다음 태스크로.

## 최종 리뷰

`../subagent-driven-development/scripts/review-package PLAN_FILE MERGE_BASE HEAD`
(MERGE_BASE = 브랜치가 갈라진 커밋, 예: `git merge-base main HEAD`) 실행하고 출력된
파일로 리뷰한다.

**서브에이전트 도구가 있으면:** requesting-code-review 스킬의
[code-reviewer.md](../requesting-code-review/code-reviewer.md)를 사용해 가장
유능한 가용 모델로 리뷰어를 파견한다 — 패키지 경로, 계획서·스펙 경로, 계획서의
Review Focus 섹션 전문, 장부의 `Ruling:` 줄들을 가리킨다. 모델을 명시한다.
이것이 전체 실행이 사는 유일한 새 컨텍스트다. 건너뛰지 말고, 내 diff 읽기로
대체하지 않는다.

**서브에이전트 도구가 없으면:** code-reviewer.md를 읽고 마지막 태스크의 장부 줄 뒤에
별도 패스로 직접 그 리뷰를 수행한다. 장부에 `Final review: self-review (no subagent tool)`을
쓰고 최종 메시지에 밝힌다: 작성자의 셀프 리뷰는 새 리뷰어보다 약하며, 충분한지는
상대방이 머지 전에 판단한다.

리뷰어의 심각도 라벨은 조언이고 게이트는 내가 쥔다. "판단 보류" 목록도 내 몫이다 —
각 줄은 판결이다. 먼저 재등급한다: 스펙은 비전 문서고, 등급은 그 소프트웨어를 쓰는
합리적인 사람이 얻는 효과로 매긴다. 그 다음:

- **Critical·Important** → 수정 패스 진입
- **Minor** → 장부에 `Final: minor (deferred): <한 줄>`로, 최종 메시지의 "보류된 minor" 아래에. minor는 수정 패스에 들어가지 않고 판결이 되지 않는다.

Critical·Important 발견은 내가 직접 고친다 — 수정 패스는 한 번. 각 수정은 TDD로
검증한다: 발견을 재현하는 테스트를 쓰고, 실패를 보고, 통과시키고, 전체 스위트를
돌린다. 장부에 `Final: fixed <발견> — <테스트명> RED→GREEN, suite <N>/<N>`으로 기록한다.
테스트 없이 실패를 먼저 보지 않은 수정은 검증된 게 아니다. 패스 뒤 스위트가 그린
아니면 패스는 끝나지 않았다. 재리뷰를 파견하지 않는다.

고치지 않기로 한 발견은 판결이다 — `Final: Ruling: <발견> — <코드가 유지되는 이유> — <틀렸을 때 비용>` —
판결 목록으로 상대방에게 닿는다. 두 번째 수정 패스는 없다.

## 마무리

삭제 전에 장부의 `Ruling:` 포함 줄을 전부 최종 메시지의 "내가 내린 판결" 아래에
순서대로 모은다 — 각각 틀렸을 때 비용과 함께. `minor (deferred)` 줄은 전부 "보류된
minor" 아래에. 둘 다 빠짐없이. 최종 메시지는 내가 상대방 대신 내린 결정들과,
조치하지 않기로 한 발견들이 그들에게 닿는 유일한 곳이다.

최종 리뷰가 깨끗하고 수정이 커밋되면 이 계획의 워크스페이스 디렉토리를 삭제한다 —
기록은 이제 git에 있다. 형제 디렉토리는 다른 계획의 것 — 손대지 않는다.

finishing-a-development-branch 스킬을 사용한다.

## 흔한 합리화

| 변명 | 현실 |
|------|------|
| "Task N이 뭔지 기억해" | 기억은 요약이다. 브리프에 정확한 값이 있다. 읽어라. |
| "계획서 코드가 맞으니 테스트 실패 보는 건 건너뛰자" | 보지 않은 테스트 실패는 아무것도 증명하지 않는다. 하나의 단계다. 실행하라. |
| "계획이 여기서 틀렸는데 그냥 옳은 대로 하자" | 옳은 대로 하고 판결을 장부에 기록한다. 기록 없는 이탈은 몰래 내린 결정이다. |
| "장부 줄은 몇 태스크 뒤에 쓰자" | 압축은 편한 때를 기다리지 않는다. 커밋과 같은 메시지에 한 줄씩. |
| "다음 태스크 전에 확인하자" | 인라인을 고른 이유는 아끼기 위해서다. 네 가지 정지만이 멈춘다. |
| "내 diff를 꼼꼼히 봤으니 최종 리뷰어는 중복이다" | 같은 작성자, 같은 사각지대. 리뷰어는 이번 실행이 사는 유일한 새 컨텍스트다. |
| "테스트는 통과하겠지, 자명한 변경이야" | "'겠지'는 증거가 아니다. 계약은 명령과 그 출력을 요구한다. |
| "리뷰어가 Minor라 했으니 Minor다" | 그 라벨은 스펙의 침묵을 등급한 것이다. 사람이 얻는 효과를 등급하라. |
| "수정이 자명하니 실패 테스트 먼저는 불필요" | 실패 테스트만이 발견이 실제였고 지금 사라졌다는 증거다. 없으면 diff와 희망뿐이다. |
