# Refit

Refit은 에이전트가 일한 **환경**을 점검한다 — 만든 코드가 아니다(그건 review·verify 관할), 한 번의 실행에서 얻은 교훈도 아니다(그건 launch의 sediment 패스 관할). 모든 작업은 마찰을 남긴다: 같은 검사에 계속 걸린 반복 루프, 신호를 기다리다 멈춘 실행, 결정적 출력이 어디에도 캡처되지 않은 디버깅 세션. Refit은 기록된 마찰을 읽어 환경 변경으로 바꾸고, 다음 실행이 더 나은 환경에서 시작하게 한다.

## Evidence first — 증거 먼저

점검은 체크리스트가 아니라 기록에서 시작한다. 사용자에게 묻기 전에 읽는다:

- **세션의 도구 호출 흐름** — 어디서 멈추고, 반복하고, 낭비성으로 분기했는지 (원본의 trace_timeline/trace_summary는 이 환경에 없으므로 대화 기록에서 회고한다)
- **세션 마찰** — 사용자 교정, 재시도, 막힘, 실패가 드러난 지점 (원본의 `omc session friction report`는 이 환경에 없으므로 대화에서 수집한다)
- **`~/workspace/` 하위 로그·상태 파일** — cron/hook 실행 로그, 상태·워터마크·설정 파일의 에러·재시도·삼켜진 실패
- **계획·런 기록** — `.omc/plans/`의 계획 문서, 목표 hidden_files의 런 리포트에 쌓인 문제들
- **레포의 검사 표면** — `package.json` 스크립트, CI 워크플로. 새 검사를 제안하기 전에 기존 것을 먼저 읽는다 — 존재하는데 연결이 안 됐거나 조용히 깨진 검사가 바로 발견이지, 재발명이 아니다

발견은 데이터가 보여주는 것에서 나온다. 빈 점검은 유효한 결과이며 그대로 말한다. 지어낸 발견은 점검을 건너뛴 것과 같은 위반이다. 연결된 자동 검사가 하나도 없는 레포는 그 자체가 발견이지 중립 상태가 아니다.

## 네 개의 수정 소유 표면

모든 발견은 수정을 소유하는 표면을 지명한다. 어떤 표면에도 안 맞는 발견은 이유와 함께 명시적으로 기각한다.

1. **결정적 검사(Deterministic check)** — 실패가 기계적이었다: 고정된 구문 패턴, 금지된 API, import 형태, 파일 위치 규칙. 수정은 린트 규칙·hook·CI 잡 — 레포의 기존 가드레일 중 가장 싼 것. 규칙을 쓰기보다 검사를 만드는 쪽이 기본값.
2. **조향 표면(Steering surface)** — 실패가 가드레일로 대체 못 하는 판단이었다: 파일 간 일관성, 주변 스타일 맞추기. 수정은 매칭되는 `docs/standards/` 볼륨, 또는 `AGENTS.md`/`CLAUDE.md`에 얇게. 장문보다 네비게이션 포인터.
3. **도구 표면(Tool surface)** — 마찰이 도구 자체였다: 비싸거나 토큰 비효율적인 호출, 빠진 자동화, 필요할 때 돌리기엔 너무 느린 검사. 수정은 cron/hook 설정, `~/workspace/scripts/`, MCP 설정.
4. **정보 표면(Information surface)** — 에이전트에게 닿지 않는 신호가 필요했다: 데브서버 로그, 서비스 상태, 서드파티 읽기 전용 접근. 수정은 로그를 틀고, 상태를 노출하고, 접근 경로를 문서화한다.

분할의 기준은 강제 압력이 어디에 사는가다: 구현 컨텍스트가 가장 많이 짊어진다(탐색·작성·디버깅 동시). 리뷰 컨텍스트는 압력 없는 diff를 받는다. 그래서 표준은 리뷰어와 검사에 속하고, 구현자에게 지시를 더 얹는 쪽으로 가지 않는다.

## 제안과 착륙 (Proposal and landing)

1. 발견을 심각도 순으로 제시 — 각각 `발견 → 표면 → 의도된 변경` 형태, 기기(인스트루먼트) 증거 한 줄과 함께.
2. 사용자 승인에서 멈춘다. 각 줄은 개별적으로 승인·거부 가능하다.
3. 승인된 발견을 각 표면에 기록한다. 조향 문장을 쓰기 전에 `agent-doc-discipline` 스킬을 읽고 그 검증 체크리스트를 적용한다. 새로 설치한 결정적 검사는 물렸음을 증명해야 착륙으로 친다: 깨끗하게 한 번 돌리고, 의도적으로 넣은 위반에서 실패하는 것을 시연하고, 위반을 원복한다. 실패하는 모습을 보일 수 없는 검사는 제안으로 돌려보낸다 — 한 번도 발화한 적 없는 가드레일은 보호가 아니라 장식이다.
4. 각 발견이 어디에 착륙했는지 기록한다 — 줄마다 파일 위치 하나. 다음 refit은 기억이 아니라 이 기록에서 시작한다.

## Headless refit (무인 호출)

Refit은 사용자가 호출하지만, 점검이 키보드에 사용자를 필요로 하진 않는다 — 처분에 필요할 뿐이다. cron 같은 스케줄러가 헤드리스 세션을 열어 이 스킬을 호출할 수 있다. 점검은 같은 계약 하에 자연 경계까지 돈다:

- 점검은 같은 기록을 읽고 어디에도 기록하지 않는다 — 헤드리스 refit은 제안 목록만 만든다. `발견 → 표면 → 의도된 변경` 형태, 각각 기기 증거 한 줄과 함께, `~/workspace/` 하위 pending 파일(예: 해당 목표의 `hidden_files/refit-pending.md`)에 쓴다. 알림 채널이 설정돼 있으면(`configure-notifications`) 요약을 통지해 점검이 대기 중임을 알린다.
- 인터랙티브 refit과 똑같이, 사용자 승인 없이 어떤 표면에도 닿지 않는다 — 제안은 순위대로 대기하고, 각각 개별 거부 가능하며, 다음 인터랙티브 refit은 점검을 다시 돌리지 않고 pending 목록에서 시작한다.
- 빈 점검은 그대로 말한다("발견 없음") — 절대 채우지 않는다.

## Output Contract

- 심각도 순 발견 목록 — 각각 증거·표면·의도된 변경 포함, 줄마다 개별 판단 가능
- 승인 후: 무엇이 어디에 착륙했는지
- 기각된 발견과 이유

## Operating Rules

- 이 스킬은 모델이 임의로 호출하지 않는다 — 사용자가 "refit 해줘"라고 직접 요청할 때만 사용한다.
- 코드 수정·단일 실행 교훈은 관할 밖이다 — review·verify·launch sediment 패스로 보낸다.
- **승인 없는 기록 금지**: 어떤 표면에도 사용자 승인 없이 쓰지 않는다. 헤드리스 실행에서도 마찬가지다.
- 빈 점검을 "발견 없음"으로 보고하는 것을 실패로 보지 않는다.
