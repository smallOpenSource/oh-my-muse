## Purpose

2~3줄짜리 간단한 아이디어 설명을 받아 전 과정을 자율적으로 처리한다. 요구사항 분석 → 기술 설계 → 계획 수립 → 병렬 구현 → QA 반복 → 다각도 검증을 거쳐 동작이 검증된 코드를 산출한다.

## Workflow

1. **확장 (Expansion)**: 사용자 아이디어를 상세 스펙으로 확장한다. 입력이 모호하면(파일 경로·함수명·구체적 근거 없음) socratic 방식으로 먼저 명확히 묻는다. 산출물: `~/workspace/.omc/autopilot/spec.md`.
   - 검증된 deep-interview 스펙(`.omc/specs/deep-interview-*.md`)이 있으면 확장 분석을 건너뛰고 그 스펙을 그대로 Phase 0 산출물로 사용한다.
   - **AFK 가정 프로토콜** (헤드리스 실행·응답 없는 확인 요청 등 사용자 답을 받을 수 없을 때): 멈추지 않고 진행하되 절대 조용히 추측하지 않는다. 인터뷰 질문이 됐을 추측은 전부 스펙의 `## Assumptions` 섹션에 기록한다 (추측 내용·근거·가역성). 되돌리기 어렵고(가역성 낮음) 실제 트레이드오프인 추측은 `~/workspace/.omc/autopilot/decisions-pending.md`에 올리고(옵션·추천·가역성 노트), 해당 범위는 가역적 방향으로만 구현하거나 연기한다. 완료 보고는 Open Assumptions를 거부 우선순위 순으로 선두에 둔다.
2. **계획 (Planning)**: 스펙으로부터 구현 계획을 만든 뒤 비평(Critic) 관점으로 검증한다. 산출물: `~/workspace/.omc/plans/autopilot-impl.md`.
   - 이미 검증된 계획(`.omc/plans/ralplan-*.md`, `.omc/plans/consensus-*.md`)이 있으면 1~2단계를 건너뛰고 실행 단계로 바로 진입.
3. **실행 (Execution)**: 계획을 독립 작업 단위로 나누어 `subagent.spawn`으로 병렬 실행한다. 간단한 작업은 가벼운 모델, 복잡한 작업은 고성능 모델에 배정한다.
4. **QA 사이클**: 빌드·린트·테스트를 돌려 실패를 수정, 최대 5회 반복한다. 같은 오류가 3회 연속이면 중단하고 근본 원인을 보고한다.
5. **검증 (Validation)**: 기능 완성도, 보안 취약점, 코드 품질을 병렬로 리뷰한다. 모든 리뷰어가 승인해야 하며, 반려 항목은 수정 후 재검증한다.
6. **정리 (Cleanup)**: 성공 시 상태 파일(`.omc/state/autopilot-state.json`, `ralph-state.json` 등)을 삭제하고 완료를 보고한다.
   - **클로즈아웃 기록**: 종료 전에 최대 3줄의 사실만 `~/workspace/.omc/notepads/autopilot/problems.md`에 추가한다 (무엇이 깨졌는지·무엇이 느렸는지). 블로커는 `issues.md`에도 추가한다. 기존 항목 보존: 추가만 하고 덮어쓰지 않는다. 관찰 내용이 없으면 쓰지 않는다. 이 관찰을 레포 표면에 반영하는 것은 `refit` 스킬의 몫이다.

## Output Contract

- 완료 시 보고 항목: 구현된 내용 요약, 변경된 파일 목록, 테스트/빌드 통과 증거, 산출물 경로.
- 중단 조건: 같은 QA 오류 3회 연속, 검증 3회 반려, 사용자 "중단해" 요청.
- 중단 시에는 진행 상황을 보존하고, 재요청 시 이어서 진행한다.
- **최종 점검**: 5단계 전부 완료 / 검증자 전원 승인 / 테스트·빌드 통과(새 출력으로 확인) / 상태 파일 정리 / 완료 보고.

## Operating Rules

- **실행 병렬화**: 독립적인 작업은 반드시 `subagent.spawn` 병렬 실행으로 처리한다. 순차 대기 금지.
- **모델 관련**: 원문의 Opus/Sonnet/Haiku 티어 지정은 Muse 환경에서는 적용되지 않는다. 작업 난이도에 따라 병렬 서브에이전트 수를 조절하는 것으로 대체한다.
- **외부 모델 불가**: 원문의 Cursor/Codex/Gemini 워커, `omc team` tmux 오케스트레이션, `cursor-agent` CLI는 이 환경에서 동작하지 않는다. 모든 실행은 `subagent.spawn` 기반으로 한다.
- **hooks 대체**: 원문의 Stop hook 강제 진행은 이 환경에 없으므로, QA/검증 사이클은 이 스킬의 Workflow 단계로 명시적으로 수행한다. 반복 작업이 필요하면 내 `hooks`/`cron`으로 대체 가능하다.
- **계획 경계**: 요구사항이 너무 모호하면 바로 코딩하지 말고 `plan` 스킬로 명확히 한 뒤 진행한다. "그냥 설명해줘" 요청에는 대화로 응답한다.
