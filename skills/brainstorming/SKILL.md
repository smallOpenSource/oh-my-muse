# 브레인스토밍

무엇을 만들지 아는 것과 실제로 원하는 것을 아는 것은 다르다. 이 스킬은
무엇을 만들지 결정하기 전에, 상대방이 실제로 원하는 것과 그 이유를 함께
파악하는 데 사용한다.

## 시작: 무엇을 알고 있는가

응답 전에 자문하라: 그들이 원하는 것과 그 이유를 얼마나 알고 있는가?

- **요청에 모든 것이 담겨 있다** ("아이콘을 cornflower blue로"). 빠르고 명확한 작업 — 그대로 수행하고 한 내용을 말한다.
- **중요한 것이 빠져 있다.** 대화를 시작한다.

## 첫 메시지

첫 메시지는 순서대로 두 가지:

1. 질문 건너뛰고 바로 시작하고 싶으면 그렇게 말해달라는 한 줄. 건너뛰겠다고 하면 이 스킬은 끝 — 중요한 구현 방식(플랫폼·언어·매체) 결정은 한 줄로 명시한 뒤 평소처럼 진행한다.
2. 묘사를 끌어내는 열린 질문 하나. 실제 순간이나 구체적 장면을 묻는다: "이게 있었으면 좋겠다고 느끼는 순간은 언제인가요?" / "그 자리에 누가 함께 있을까요?"

## 대화

메시지마다 질문 하나로 끝낸다: 예시 답안 목록을 달지 않은 한 문장. 평이한 말로, 상대방보다 살짝 위에 맞춰 쓴다. 상대방의 어휘를 따라가고 절차 용어는 쓰지 않는다.

**묘사를 끌어내라.** 열린 질문이 먼저. 그들 자신의 말이 의도를 담는다. 막혔을 때만 짧은 메뉴를 준다. "그냥 추측해줘"/"어떻게 생각해?"라고 하면 구체적인 제안을 내놓는다.

**구현 방식.** 모든 프로젝트는 매체·도구·자원 선택 위에 선다. 어떤 선택은 그들이 하고 싶어하고, 어떤 선택은 맡기고, 이미 갖고 있는 것은 무엇인지 일찍 파악한다. 기존 작업이 있으면 그 위에서 쌓는다. 내가 내린 선택은 설계서에 내 결정으로 기록한다 — 그들이 동의한 것처럼 적지 않는다.

**다룰 영역** (스크립트가 아닌 영역 — 읽어주지 않는다):

- 무엇을 만드는지, 무엇이 특별한지
- 왜 지금인지, 성공이 그들에게 어떤 모습인지
- 목표·비목표·반목표 (기술적으로 돌아가도 실패인 경우)
- 레퍼런스: 다른 곳에서 보고 좋아했거나 싫어한 것
- 현재 상태: 지금 있는 것, 시도해본 것
- 그들이 신경 쓰는 디테일

**잘 통하는 질문**은 구체에 닻을 내린다: "지난번에 그랬던 과정을 처음부터 말해줘요", "둘 중 하나만 잘할 수 있다면 어느 쪽?", "제가 뭘 잘못하면 가장 아쉬울까요?" 추측해서 고쳐달라고 하는 방식도 효과적이다.

**탐색 제안을 한다.** 어느 정도 기반이 잡히고 직접 보는 게 도움이 되면 조사를 제안한다: 코드베이스, 그들의 파일·데이터, 웹. 무엇을 볼지 말한다. 갈지 말지는 그들이 정한다.

**속으로는 넓게 생각한다.** 제안하기 전에 여러 아이디어를 내고 약한 것을 버린다 — 그들이 말한 이유와 충돌하는 것도. 비교 표는 결정에 도움이 될 때만 보여준다.

**보여주지 말고 말하라.** 직접 보는 것이 읽는 것보다 낫다면 비주얼 동반자(아래)를 제안한다: 화면·페이지·인쇄물, 레이아웃, 흐름·순서, 나란히 비교할 옵션, 그림이 글보다 쉬운 구조.

**스파이크를 쓴다.** 에이전트 작업은 폭포수지만 매우 빠르다. 일회용 빠른 빌드가 가장 싼 학습 수단일 때가 많다. 도움이 되면 제안한다. 스파이크는 테스트를 생략하거나 최소로, 견고함을 생략하고, 계획·구현·리뷰 절차를 건너뛴다. 배운 것은 대화로 가져온다.

## 되돌려 말하기 (Playback)

이해한 부분은 바로 되돌려 말한다. 한 파트를 200~300자 정도로 설명한 뒤 다음 파트 질문으로 돌아간다. 되돌려 말하기와 질문이 번갈아 이어지고, 마지막 청크는 남은 부분을 다룬다.

추측은 추측으로 표시하고, 그들이 말한 것만 그들의 것으로 기록한다. 각 청크 끝에는 무엇이 틀리거나 빠졌는지 묻는다.

## 작업 크기 정하기

원하는 바를 파악했으면 크기를 정해 평이하게 말한다. 그들은 덮어쓸 수 있다.

| 크기 | 전체 설명 | 다음 |
|------|-----------|------|
| 빠르고 명확한 작업 | 요청 자체 | 바로 수행 |
| 작은 변경 | 채팅 안에서 | 일반 워크플로로 구현 |
| 설계서가 필요한 프로젝트 | 설계서 문서 | 전체 계획 (소프트웨어: writing-plans 스킬) |

도중에 커지면 멈추고, 그렇다고 말하고, 한 단계 올린다.

## 설계서

프로젝트라면, 그 분야의 유능한 빌더가 상대방에게 되묻지 않고 계획할 수 있는 평이한 문서를 쓴다. 포함 내용:

- 의도와 이유
- 목표·비목표·반목표
- 제약
- 그들이 정한 구현 방식 결정 (정해진 대로)
- 빌더에게 남은 것

**위치:** 소프트웨어 레포라면 `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md`에 커밋. 그 외는 물어본다.

**빌더 체크:** 이 디렉토리의 `builder-check-prompt.md`를 담은 새 서브에이전트를 실행한다. 설계서를 쓴다고 말할 때 리뷰어가 먼저 읽을 것이고 한 번 질문이 돌아올 수 있다고 알린다. 체크가 돌아오기 전까지 문서를 넘기지 않는다. 빌더 질문을 세 더미로 분류:

- **이미 답 있음**: 대화나 프로젝트에 답이 있다 → 문서에 반영
- **사소함**: 합리적인 빌더가 알아서 정할 수 있다 → 내가 정하고 내 결정으로 표시
- **그들의 몫**: 그들만 답할 수 있고 답에 따라 만들 것이 달라진다 → 모아 한 번에 묻는다 (중요한 순서대로). 답을 문서에 반영하고, 내가 한 결정 목록과 함께 넘긴다. 체크가 만드는 질문은 이 한 번뿐이다.

<HARD-GATE>
상대방이 전체 설명을 승인하기 전에는 아무것도 만들지 않는다. 채팅 안의 작은 변경은 채팅 승인, 프로젝트는 설계서 문서 승인이 기준. 만드는 것에는 제품 코드 작성·스캐폴딩·의존성 설치·프로젝트 생성·구현 스킬 호출이 포함된다. 읽고 탐색하는 것은 괜찮다.

예외 둘. 질문을 건너뛰기로 했다면 스킬은 끝이고 게이트도 함께 끝난다. 그들이 승인한 스파이크는 만들 수 있다 — 일회용으로 표시하고, 만든 것을 유지하는 것은 게이트를 다시 거치는 새 요청이다.

프로젝트 설계서가 승인되면 다음은 계획이다. 소프트웨어라면 writing-plans 스킬만 호출한다.

## 경고 신호

| 생각 | 현실 |
|------|------|
| "옵션을 주면 수고를 덜어준다" | 옵션은 유도한다. 먼저 묘사해달라. |
| "합리적인 기본값을 채워 넣자" | 좋다. 단, 말로 꺼내라. 듣지 못한 기본값은 거절할 수 없던 것이다. |
| "절차부터 설명해야겠다" | 질문부터 하라. 절차는 드러난다. |
| "'좋은데요'는 승인이다" | 승인은 보여준 것에만 적용된다. 쓰지 않은 설명은 승인된 게 아니다. |
| "스파이크가 돌아가니 계속 쌓자" | 유지하는 것은 새 요청이다. 게이트를 다시 거친다. |

**딱 필요할 때 제안한다.** 위 순간이 처음 왔을 때 한 번, 앞에 제안하지 않는다. 제안은 그 자체로 한 메시지:

> "보여드리면서 하면 더 쉬울 것 같아요. 모형을 볼 수 있는 브라우저 탭을 열어드릴까요?"

거절하면 텍스트로 진행하고, 그들이 다시 꺼내기 전에는 제안하지 않는다.

**[환경 한계]** 이 환경에서는 비주얼 동반자를 지원하지 않는다 — 로컬 브라우저 탭·WebSocket 동반 서버(`scripts/server.cjs`)를 띄울 방법이 없다. 목업이 필요하면 정적 HTML 아티팩트로 만들고 스크린샷으로 검증하라. 참고: `server.cjs`는 원격 텔레메트리 전송이 아니라 로컬 동반 서버이며, 브랜드 로고 이미지 하나를 외부 URL(`primeradiant.com`)에서 불러온다 — 이 환경에서 서버를 실행하지 않으므로 외부 전송은 발생하지 않는다.
