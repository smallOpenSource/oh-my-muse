# 브레인스토밍

무엇을 만들지 아는 것과 실제로 원하는 것을 아는 것은 다르다. 이 스킬은
무엇을 만들지 결정하기 전에, 상대방이 실제로 원하는 것과 그 이유를 함께
파악하는 데 사용한다.

## 시작: 무엇을 알고 있는가

응답 전에 자문하라: 그들이 원하는 것과 그 이유를 얼마나 알고 있는가?

- **요청에 모든 것이 담겨 있다** ("아이콘을 cornflower blue로"). 빠르고 명확한 작업 — 그대로 수행하고 한 내용을 말한다.
- **중요한 것이 빠져 있다.** 대화를 시작한다.

구현을 시작하기 전, 순서대로 반드시:

1. 구현 방식을 별도 메시지로 나열하고 상대방이 하나를 고르게 한다 (구현 방식 목록 참조).
2. 설계서를 쓴다 — 짧게 또는 전부 (작업 크기 정하기 참조).
3. 그 설계서 승인을 받는다.
4. writing-plans 스킬을 호출한다.

구현이 아닌 것 둘: 상대방이 승인한 스파이크 (스파이크로 감 잡기 참조), 질문 건너뛰기를 선택한 뒤 요청대로 하는 것.

## 묻기 전에 살펴보기

기존 프로젝트이거나 상대방이 맥락(스펙·계획·인수인계·가리킨 파일·이전 대화)을 줬으면, 첫 메시지 전에 파고든다. 가리킨 것과 연결된 코드·자료를 읽고, 관련 부분이 지금 어떻게 동작하고 변경이 무엇을 건드릴지 설명할 수 있을 때까지 읽는다. 프로젝트나 맥락이 이미 답하는 것은 묻지 않는다.

## 첫 메시지

다음 중 하나로 일을 앞으로 움직인다:

- **이미 원하는 바를 말했다** (스펙·계획·자세한 요청): 전체 메시지 약 200자 목표. 요청을 내 말로 되돌려 말해 형태를 확인하게 한다: 원하는 것·대상·이유, 말한 범위 안에서. 찾은 것 중 관련 있는 것을 덧붙인다: 관련 부분의 현재 동작과 변경이 건드릴 것. 요청이나 구현 방식을 바꿀 수 있는 것 — 제약·충돌·더 싼 경로 — 을 찾았으면 plain하게 말한다. 구현 방식은 원하는 바를 파악한 뒤에 나온다 (구현 방식 목록 참조). 정정 요청 한 줄로 끝내고, 원하는 바에 대한 질문 하나: 요청이 열어둔 것 중 답이 만들 것을 가장 바꾸는 것. 스펙은 종종 불완전하니, 그 위에 짓기 전에 확인한다.
- **아직 말하지 않았다:** 요청이 정하지 않은 가장 큰 것에 대해, 그들의 말로 하는 열린 질문 하나. 왜 묻는지 말한다: 답이 만들 것을 어떻게 바꾸는지. "빵집 웹사이트"라면: "대부분 찾아올지 고민하는 사람용이면 영업시간과 오늘 진열 상품을 앞에 두겠고, 주문까지 받으면 다른 사이트예요. 들어왔을 때 무엇을 하게 하고 싶으세요?"

메시지 끝은 브레인스토밍을 요청했는지로 갈린다:

- **요청했다** (이름으로·호출로·설계 논의 요청으로): 질문으로 끝낸다. 대화를 원한다.
- **요청하지 않았다:** 대화를 원하지 않을 수 있다. 질문 뒤에 바로 시작하자는 가벼운 한 줄 제안을 덧붙인다, "그냥 바로 시작하는 게 나으면 그렇게 말해줘요." 같은. 받아들이면 이 스킬은 끝 — 중요한 구현 방식 결정(플랫폼·언어·매체)은 한 줄로 명시한 뒤 평소처럼 진행한다.

## 대화

메시지마다 질문 하나로 끝낸다: 예시 답안 목록을 달지 않은 한 문장. 평이한 말로, 상대방보다 살짝 위에 맞춰 쓴다. 상대방의 어휘를 따라가고 절차 용어는 쓰지 않는다. 이 스킬을 상대방에게 인용할 필요는 없다.

**묘사를 끌어내라.** 열린 질문이 먼저. 그들 자신의 말이 의도를 담는다. 막혔을 때만 짧은 메뉴를 준다. "그냥 추측해줘"/"어떻게 생각해?"라고 하면 구체적인 제안을 내놓는다.

**구현 방식.** 모든 프로젝트는 매체·도구·자원 선택 위에 선다. 어떤 선택은 그들이 하고 싶어하고, 어떤 선택은 맡기고, 이미 갖고 있는 것은 무엇인지 일찍 파악한다. 기존 작업이 있으면 그 위에서 쌓는다. 내가 내린 선택은 설계서에 내 결정으로 기록한다 — 그들이 동의한 것처럼 적지 않는다.

**다룰 영역** (스크립트가 아닌 영역 — 읽어주지 않는다):

- 무엇을 만드는지, 무엇이 특별한지
- 왜 지금인지, 성공이 그들에게 어떤 모습인지
- 목표·비목표·반목표 (기술적으로 돌아가도 실패인 경우)
- 레퍼런스: 다른 곳에서 보고 좋아했거나 싫어한 것
- 현재 상태: 지금 있는 것, 시도해본 것
- 그들이 신경 쓰는 디테일

**질문은 구체적으로.** 프로젝트와 그들이 말한 것에 맞춘다. 날카로운 동료처럼 소크라테스식으로 묻는다: 지난 답이나 찾은 것에 질문을 세워, 놓쳤을 수 있는 결과나 경우를 생각하게 한다 ("투표는 회의 전에 마감하고, 이번 달에 두 명이 새로 들어왔어요. 중간에 들어온 사람도 투표하나요?"). 이유가 이미 분명하지 않으면 무엇을 배우려는지, 답이 무엇을 바꾸는지 말한다. 고칠 수 있는 제안과 그 이유가 질문보다 나을 때가 많다.

**탐색 제안을 한다.** 어느 정도 기반이 잡히고 더 파고드는 게 도움이 되면 조사를 제안한다: 코드베이스 더 깊이, 그들의 파일·데이터, 웹. 무엇을 볼지 말한다. 갈지 말지는 그들이 정한다.

**구현 방식 목록.** 원하는 바를 파악했으면, 쓰기 전에 구현 방식을 별도 메시지로 나열한다. 실제로 가능한 대안을 여러 개 내고 약한 것을 버린다 — 원하는 이유와 충돌하는 것, 기존 작업이 배제하는 것 포함. 남은 두세 개를 제시하고, 각각 프로젝트 실제 동작에 근거해 무엇을 주고받는지 말한다. 하나를 추천하고 이유를 말한 뒤 어느 쪽으로 갈지 묻는다. 진짜로 합리적인 방식이 하나뿐이면 그렇게 말하고 다른 방식이 안 맞는 이유를 설명한다. 이것은 구현 방식에 대한 것 — 원하는 바는 먼저 묘사로 파악한다.

**보여주지 말고 말하라.** 직접 보는 것이 읽는 것보다 낫다면 비주얼 동반자(아래)를 제안한다: 화면·페이지·인쇄물, 레이아웃, 흐름·순서, 나란히 비교할 옵션, 그림이 글보다 쉬운 구조.

**스파이크를 쓴다.** 에이전트 작업은 폭포수지만 매우 빠르다. 일회용 빠른 빌드가 가장 싼 학습 수단일 때가 많다. 도움이 되면 제안한다. 스파이크는 테스트를 생략하거나 최소로, 견고함을 생략하고, 계획·구현·리뷰 절차를 건너뛴다. 배운 것은 대화로 가져온다.

## 되돌려 말하기 (Playback)

이해한 부분은 바로 되돌려 말한다. 한 파트를 200~300자 정도로 설명한 뒤 다음 파트 질문으로 돌아간다. 되돌려 말하기와 질문이 번갈아 이어지고, 마지막 청크는 남은 부분을 다룬다.

그들이 말한 것만 그들의 것으로 기록한다. 내가 채운 것은 내 제안으로, 이유와 함께 기록한다. 각 청크 끝에는 무엇이 틀리거나 빠졌는지 묻는다.

청크를 보내기 전 확인한다: 페이지·화면·일정·인쇄물처럼 그들이 볼 것을 설명하는가? 그렇고 비주얼 동반자 제안을 아직 하지 않았다면, 청크를 다음 메시지로 미루고 제안 메시지부터 보낸다. 수락했으면 설명 옆에 목업을 둔다.

## 작업 크기 정하기

원하는 바를 파악하고 상대방이 구현 방식을 골랐으면, 크기를 평이하게 말한다. 그들은 덮어쓸 수 있다.

| 크기 | 설계서 |
|------|--------|
| 작은 변경 | 짧은 것: 함께 다룬 내용을 글로 정리한 것 |
| 프로젝트 | 아래의 전체 설계서 |

짧든 전부든, 설계서에는 **구현 방식** 부분이 있다: 고려한 두세 가지 방식, 각각의 주고받음, 그들이 고른 것, 이유. 대화에서 먼저 고르고, 그 뒤에 설계서를 쓴다.

도중에 커지면 멈추고, 그렇다고 말하고, 한 단계 올린다.

## 설계서

프로젝트라면, 그 분야의 유능한 빌더가 상대방에게 되묻지 않고 계획할 수 있는 평이한 문서를 쓴다. 포함 내용:

- 의도와 이유
- 목표·비목표·반목표
- 제약
- 구현 방식 (위 참조)
- 그들이 정한 구현 방식 결정 (정해진 대로)
- 빌더에게 남은 것

작은 변경의 짧은 설계서는 같은 항목을 한두 줄씩 다루고, 빌더 체크 없이 상대방에게 바로 간다.

**위치:** 소프트웨어 레포라면 `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md`에 커밋. 그 외는 물어본다.

**빌더 체크** (프로젝트만): 이 디렉토리의 `builder-check-prompt.md`를 담은 새 서브에이전트를 실행한다. 설계서를 쓴다고 말할 때 리뷰어가 먼저 읽을 것이고 한 번 질문이 돌아올 수 있다고 알린다. 체크가 돌아오기 전까지 문서를 넘기지 않는다. 빌더 질문을 세 더미로 분류:

- **이미 답 있음**: 대화나 프로젝트에 답이 있다 → 문서에 반영
- **사소함**: 합리적인 빌더가 알아서 정할 수 있다 → 내가 정하고 내 결정으로 표시
- **그들의 몫**: 그들만 답할 수 있고 답에 따라 만들 것이 달라진다 → 모아 한 번에 묻는다 (중요한 순서대로). 답을 문서에 반영하고, 내가 한 결정 목록과 함께 넘긴다. 체크가 만드는 질문은 이 한 번뿐이다.

<HARD-GATE>
상대방이 설계서를 승인하기 전에는 아무것도 만들지 않는다. 작은 변경은 짧은 설계서, 프로젝트는 전체 설계서 승인이 기준. 만드는 것에는 제품 코드 작성·스캐폴딩·의존성 설치·프로젝트 생성·구현 스킬 호출이 포함된다. 읽고 탐색하는 것은 괜찮다.

예외 둘. 질문을 건너뛰기로 했다면 스킬은 끝이고 게이트도 함께 끝난다. 그들이 승인한 스파이크는 만들 수 있다 — 일회용으로 표시하고, 만든 것을 유지하는 것은 게이트를 다시 거치는 새 요청이다.

프로젝트 설계서가 승인되면 다음은 계획이다. 소프트웨어라면 writing-plans 스킬만 호출한다.
</HARD-GATE>

## 경고 신호

| 생각 | 현실 |
|------|------|
| "원할 만한 것들의 메뉴를 주면 수고를 덜어준다" | 옵션은 유도한다. 먼저 묘사해달라. |
| "합리적인 기본값을 채워 넣자" | 좋다. 단, 말로 꺼내라. 듣지 못한 기본값은 거절할 수 없던 것이다. |
| "질문에 답했으니 설계서를 쓰자" | 먼저 구현 방식을 별도 메시지로 나열하라. |
| "절차부터 설명해야겠다" | 질문부터 하라. 절차는 드러난다. |
| "'좋은데요'는 승인이다" | 승인은 보여준 것에만 적용된다. 쓰지 않은 설계서는 승인된 게 아니다. |
| "스파이크가 돌아가니 계속 쌓자" | 유지하는 것은 새 요청이다. 게이트를 다시 거친다. |

## 비주얼 동반자

모형·다이어그램·프로토타입을 보여주는 브라우저 탭. 도구이지 모드가 아니다.

**딱 필요할 때 제안한다.** 위 순간이 처음 왔을 때 한 번, 앞에 제안하지 않는다. 제안은 그 자체로 한 메시지:

> "보여드리면서 하면 더 쉬울 것 같아요. 모형을 볼 수 있는 브라우저 탭을 열어드릴까요?"

거절하면 텍스트로 진행하고, 그들이 다시 꺼내기 전에는 제안하지 않는다.

**질문마다 묻는다: 보는 게 이해에 도움이 되는가?** 목업·레이아웃·다이어그램·나란히 비교는 브라우저로. 요구사항·범위·주고받음·개념 선택은 텍스트로. UI 주제 질문이 자동으로 비주얼 질문은 아니다.

**[환경 한계]** 이 환경에서는 비주얼 동반자를 지원하지 않는다 — 로컬 브라우저 탭·WebSocket 동반 서버(`scripts/server.cjs`)를 띄울 방법이 없다. 목업이 필요하면 정적 HTML 아티팩트로 만들고 스크린샷으로 검증하라. 참고: `server.cjs`는 원격 텔레메트리 전송이 아니라 로컬 동반 서버이며, 브랜드 로고 이미지 하나를 외부 URL(`primeradiant.com`)에서 불러온다 — 이 환경에서 서버를 실행하지 않으므로 외부 전송은 발생하지 않는다.
