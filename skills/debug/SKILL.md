# Debug

## Purpose

사용자가 겪고 있는 현재 세션/레포의 문제, 워크플로우 깨짐, 이해 안 되는 런타임 동작의 원인을 찾는다. 목표: 실패 신호를 빠르게 찾아내고, 다음으로 할 가장 작은 수정/검증 단계를 설명한다.

## Workflow

1. 사용자의 문제 설명을 정확히 읽는다. (`debug` 채팅 트리거 뒤에 붙은 `$ARGUMENTS` 상당 인자를 그대로 사용)
2. 가장 관련 있는 로컬 증거부터 본다:
   - 로그·실행 기록 (exec 결과, cron/hook 실행 로그)
   - 상태 파일 (`~/workspace/` 아래 상태·워터마크·설정 파일)
   - 메모리·노트 (`muse.memory_search`, `MEMORY.md`, 일일 노트)
   - 실패한 테스트·명령어 재실행
3. 가능하면 문제를 좁게 재현한다.
4. 증상과 근본 원인을 구분한다.
5. 가장 작은 다음 수정 또는 검증 단계를 권고한다.

## Output Contract

- 관찰된 실패 (Observed failure)
- 근본 원인 가설 (Root-cause hypothesis)
- 그 가설의 증거 (Evidence)
- 가장 작은 다음 액션 (Smallest next action)

## Operating Rules

- 추측보다 실제 증거를 우선한다.
- 오케스트레이션·hook·에이전트 흐름 문제면 로그·상태 파일을 먼저 확인한다. (원본 OMC의 trace/state 전용 도구는 이 환경에 없으므로 대체 수단으로 읽는다)
- 제품/런타임 버그가 앱 코드 문제라면 그대로 말한다.
- 실패를 분리하기 전에는 광범위한 리라이트를 처방하지 않는다.
- 임시 디버그 출력에는 `[DEBUG-<4hex>]` 태그를 붙인다 — 나중에 단일 grep으로 정리한다.
- 로그·트레이스가 세션을 벗어나기 전에 시크릿을 redact한다.
- 실패 원인이 빠지거나 잘못된 seam(이음매)이면, 그 자체를 발견으로 보고하고 `refit`이나 `architecture-survey`를 가리킨다 — 환경에 대한 교훈이 개별 수정보다 오래 간다.
- 증거 없이 "다 고쳤다"고 단정하지 않는다.
