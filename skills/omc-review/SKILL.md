# Review

## Purpose

이미 존재하는 작업을 평가한다. 리뷰는 자신이 판단하는 변경을 직접 작성하지 않는다. `ai-slop-cleaner`(~/workspace/skills/ai-slop-cleaner/)는 이 리뷰 워크플로 안의 opt-in 정리 레인이다.

## Workflow

1. 무엇이 바뀌었고, 원래 의도가 무엇이었는지 확정한다.
2. 의도 대비 변경 내용을 읽는다.
3. 정확성 → 리스크 → 단순화 순으로 확인한다.
4. 각 후보 지적은 보고 전에 검증(재현)한다.
5. 심각도 높은 순으로 보고한다.

## Output Contract

- 발견 사항 (심각도 순, 각각 파일·줄·구체적 실패 시나리오 포함)
- 확인했고 깨끗했던 항목
- 평가할 수 없었던 것

## 두 축, 분리 실행 (Two axes, run apart)

상당한 규모의 diff는 두 개의 병렬 서브에이전트 패스로 리뷰하고, 결과는 따로 보고한다 — 합치거나 축을 넘나들며 재정렬하지 않는다. 한 축은 통과하고 다른 축은 실패할 수 있기 때문이다(표준은 지키지만 동작이 틀린 경우, 의도에는 충실하지만 컨벤션을 깨는 경우).

- **표준 축(Standards axis)**: 레포의 문서화된 표준 + 판단이 필요한 최소 smell 기준선에 대조. 도구가 이미 강제하는 것은 건너뛴다. 표준 집합은 발견하는 것이지 가정하는 것이 아니다: 레포에서 표준 문서(`CLAUDE.md`/`AGENTS.md`, `docs/standards/`, `CONTRIBUTING.md`, `CODING_STANDARDS.md` 또는 동등물)를 검색하고, 존재하는 것에 대해서만 리뷰한다 — 찾지 않은 표준 파일은 적용하지 않은 표준이다.
- **의도 축(Intent axis)**: 작업의 의도(작업 지시, 스펙, 티켓의 수락 기준)에 대조 — 빠지거나 부분적인 요구사항, 아무도 요구하지 않은 동작. 각 지적은 근거 줄을 인용한다.

각 서브에이전트는 ~400단어 내외로 간결하게, 하나의 축에만 집중한다(`subagent.spawn` 병렬 실행). 축별 판정을 따로 명시하고, 축을 넘나드는 단일 승자를 뽑지 않는다 — 그 재정렬을 막는 것이 분리의 목적이다. 작은 diff는 단일 패스로 충분하다.

## Operating Rules

- 체크 항목: **정확성**(로직 결함, 엣지 케이스, 에러 경로, 동시성) / **리스크**(보안 경계, 파괴적 작업, 데이터 무결성) / **재사용**(기존 유틸·패턴을 썼어야 하는 경우) / **단순화**(삭제·축소 가능한 코드) / **커버리지**(테스트 없이 출고되는 동작)
- 레인 분리: 리뷰어와 작성자가 같은 활성 컨텍스트면 안 된다. 심층 세션에서는 별도 서브에이전트(subagent.spawn)로 리뷰를 돌리고, 같은 컨텍스트에서 수행할 수밖에 없으면 "자신의 작업을 스스로 승인하지 않음" 원칙을 명시한다.
- 보고 전 검증: 재현되지 않는 그럴듯한 지적은 노이즈다.
- 심각도를 정직하게 매긴다. 철저해 보이려고 목록을 부풀리지 않는다.
- 작업물이 건전하면 "발견 없음"도 유효한 결과다.
- 기본은 조언(advisory): 리뷰는 정보를 줄 뿐 게이트가 아니다. 릴리스·보안·파괴적 작업 같은 하드 게이트는 별도이며 fail-closed(불확실하면 차단)이다.
