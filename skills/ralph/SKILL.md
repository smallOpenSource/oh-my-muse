## Purpose

복잡한 작업이 "대충 완성"으로 선언되는 것을 방지한다. 작업을 테스트 가능한 사용자 스토리로 나눈 PRD(`prd.json`)를 만들고, 각 스토리가 검증 기준을 통과할 때까지 스토리 단위로 반복 실행한다. 리뷰어 검증과 deslop 정리 패스까지 마쳐야 완료된다.

## Workflow

1. **PRD 초기화** (첫 반복만): PRD 파일이 없으면 스캐폴드를 생성한 뒤, 반드시 과제 특화 스토리와 검증 가능한 수락 기준(예: "함수 X가 입력 Z에 Y를 반환", "경로 P에 테스트 파일이 있고 통과")으로 정제한다. 포괄적 문구("구현 완료")는 PRD 쇼잉이므로 금지. 상태 기록용 `progress.txt`도 초기화한다.
2. **다음 스토리 선택**: `passes: false`인 최고 우선순위 스토리를 현재 작업으로 정한다.
3. **구현**: 독립 작업은 `subagent.spawn` 병렬 실행. 난이도에 따라 단순 조회→가벼운 서브에이전트, 표준 작업→중간, 복잡 분석→고성능으로 배정한다. 빌드·설치·테스트는 백그라운드 실행.
4. **수락 기준 검증**: 각 스토리의 활성 수락 기준을 하나씩, 최신 증거(테스트·빌드·린트 출력)로 확인한다.
   - 구현이 기준 자체를 사실로 뒤집으면(측정값이 계획과 다름) 기준을 조용히 삭제하지 말고, 원문을 보존한 채 `criterionAmendments` 장부에 kind(대체/무효)/원문/사유/증거/작성자/시간을 기록하고 수정된 기준으로 계속 검증한다.
5. **스토리 완료 표시**: 모든 활성 기준 검증 시 `passes: true`로 표시하고 `progress.txt`에 구현 내용·변경 파일·학습을 기록한다.
6. **PRD 완료 확인**: 미완료 스토리가 있으면 2단계로 돌아간다. 전부 완료면 7단계로.
7. **리뷰어 검증**: 변경 규모에 따라 적절한 깊이로, PRD의 구체적 수락 기준을 기준으로 승인/반려. 변경 파일만이 아니라 관련 호출자·호출 대상·공유 타입까지 본다. 반려 시 수정 후 같은 리뷰어로 재검증한다.
8. **Deslop 패스** (승인 후 무조건): 변경된 파일 범위에 한해 코드 정리 패스를 수행한 뒤, 회귀 테스트·빌드·린트를 다시 돌려 통과를 확인한다.
9. **종료**: 모든 검증 통과 후 상태 파일을 정리하고 완료를 보고한다.

## Output Contract

- 완료 보고 항목: 각 스토리의 통과 증거, 테스트/빌드/린트 최신 출력, 리뷰어 승인 결과, deslop 패스 결과, 변경 파일 목록.
- 절대 "그럴듯해 보인다"식의 증거 없는 완료 선언 금지.
- 차단 조건: 근본적 블로커(자격 증명 누락, 요구사항 불명확, 외부 서비스 장애), 같은 문제 3회 이상 반복, 사용자 "중단해" 요청.

## Operating Rules

- **작업 계속 규칙**: 완료 약속이 출력되지 않으면 작업을 계속한다. 승인된 검증 결과를 "보고 후 대기" 체크포인트로 취급하지 말고, 7→8→9단계를 같은 흐름에서 이어간다.
- **외부 모델 불가**: 원문의 `--critic=codex`(Codex CLI 리뷰), Cursor 워커, `omc ask`는 이 환경에서 동작하지 않는다. 리뷰는 내부 `subagent.spawn` 서브에이전트로만 수행한다.
- **hooks 대체**: 원문의 Stop hook 강제 지속(`ralph-state.json`, "The boulder never stops")은 이 환경에 없으므로, 반복 루프는 이 스킬 Workflow의 6단계로 명시적으로 수행한다. 세션 지속이 필요하면 내 `hooks`를 대체 수단으로 사용한다.
- **병렬 실행**: `Task(subagent_type=...)` 원문 표기는 전부 `subagent.spawn`으로 치환한다. tmux/팀 런타임 언급은 적용하지 않는다.
- **경로 치환**: 원문의 `.omc/` 경로는 프로젝트 기준 `~/workspace/.omc/`에 대응한다.
