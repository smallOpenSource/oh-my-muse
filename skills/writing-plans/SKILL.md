# 계획서 작성

## 개요

이 코드베이스도 이 스펙도 본 적 없는 엔지니어를 위한 구현 계획을 쓴다.
그 엔지니어는 정확한 인터페이스와 정확한 테스트만 알면 프로젝트 언어의
관용적 코드를 쓰고, 계획이 열어 둔 곳에서는 합리적 선택을 한다고 가정한다.
그들이 알 수 없는 것은 당신의 결정이다: 어떤 파일, 어떤 이름과 시그니처,
스펙의 어떤 값, 각 태스크를 증명하는 테스트. 그것을 문서화한다. 전체 계획을
한입 크기의 태스크로 나눈다. DRY. YAGNI. TDD. 잦은 커밋.

**시작 시 알린다:** "writing-plans 스킬을 사용해 구현 계획을 만듭니다."

**컨텍스트:** 격리된 워크트리에서 작업한다면, 실행 시점에 using-git-worktrees 스킬로 만든 것이어야 한다.

**계획서 저장 위치:** `docs/superpowers/plans/YYYY-MM-DD-<feature-name>.md`
- (계획서 위치에 대한 사용자 선호가 기본값을 덮어쓴다)

## 범위 점검

스펙이 여러 독립 하위 시스템을 다루면 브레인스토밍 단계에서 하위 프로젝트
스펙으로 쪼갰어야 한다. 쪼개지 않았다면 별도 계획으로 나누자고 제안한다 — 하위
시스템당 하나씩. 각 계획은 그 자체로 동작하고 테스트 가능한 소프트웨어를 만든다.

## 파일 구조

태스크를 정의하기 전에, 어떤 파일이 만들어지고 수정되는지, 각각의 책임이
무엇인지 먼저 그린다. 분해 결정이 여기서 확정된다.

- 경계가 명확하고 인터페이스가 잘 정의된 단위로 설계한다. 파일 하나에 책임 하나.
- 책임으로 나누고 기술 계층으로 나누지 않는다.
- 기존 코드베이스에서는 확립된 패턴을 따른다.

## 태스크 크기 조정

태스크는 자체 테스트 사이클을 갖고, 새로운 리뷰어 게이트를 받을 만한 최소
단위다. 태스크 경계를 그을 때: 설정·스캐폴딩·문서 단계는 산출물이 필요한
태스크에 접고, 리뷰어가 이웃 태스크를 승인하면서 이 태스크만 의미 있게 거절할
수 있는 곳에서만 나눈다. 각 태스크는 독립적으로 테스트 가능한 산출물로 끝난다.

## 단계 세분화

**각 단계는 확인할 수 있는 결과를 가진 하나의 행동:**
- "실패하는 테스트를 쓴다" - 단계
- "실행해서 실패를 확인한다" - 단계
- "통과하는 최소 코드를 구현한다" - 단계
- "테스트를 실행해 통과를 확인한다" - 단계
- "커밋한다" - 단계

## 계획서 헤더

**모든 계획서는 반드시 이 헤더로 시작한다:**

```markdown
# [Feature Name] 구현 계획

> **에이전트 작업자에게:** 필수 하위 스킬: 이 계획을 태스크 단위로 구현할 때는
> subagent-driven-development (권장) 또는 executing-plans 스킬을 사용하라.
> 단계는 추적용 체크박스(`- [ ]`) 문법을 사용한다.

**Goal:** [무엇을 만드는지 한 문장]

**Architecture:** [접근 방식 2-3문장]

**Tech Stack:** [핵심 기술/라이브러리]

**Spec:** [이 계획이 구현하는 스펙/설계서 경로 — 계획은 스펙에서 논증을
펼치므로 스펙이 함께 이동한다. 실행자는 둘 다 읽는다]

## Global Constraints

[스펙의 프로젝트 전역 요구사항 — 버전 하한, 의존성 제한, 네이밍·카피 규칙,
플랫폼 요구 — 한 줄에 하나씩, 스펙의 정확한 값을 그대로 복사. 모든 태스크의
요구사항은 암묵적으로 이 섹션을 포함한다]

## Review Focus

[스펙이 암시하지만 어떤 태스크의 테스트도 다루지 않는, 실제 사용자가 맞닥뜨릴
가능성이 가장 큰 입력 클래스·실패 모드 5개 — 한 줄에 하나씩, 입력/조건과 합리적인
사람이 기대할 동작을 명시, 가능성 높은 순. 스펙은 비전 문서다: 소프트웨어가 해야
할 일을 말하지, 마주할 모든 것을 말하지는 않는다. 스펙이 어떤 입력에 침묵하는 것은
그 입력이 깨져도 된다는 허락이 아니다. 스펙을 앞에 두고 목록을 한 번만 쓴다. 그런
다음 각 줄에 대해, 그 코드를 소유한 태스크에 그 입력을 고정하는 테스트를, 해당
태스크의 단계 스타일로 추가한다]

---
```

## 태스크 구조

````markdown
### Task N: [컴포넌트 이름]

**Files:**
- Create: `exact/path/to/file.py`
- Modify: `exact/path/to/existing.py:123-145`
- Test: `tests/exact/path/to/test.py`

**Interfaces:**
- Consumes: [이전 태스크에서 쓰는 것 — 정확한 시그니처]
- Produces: [이후 태스크가 의존하는 것 — 정확한 함수 이름, 파라미터·반환 타입.
  태스크 구현자는 자기 태스크만 본다. 이 블록이 이웃 태스크가 쓰는 이름과 타입을
  배우는 통로다]

- [ ] **Step 1: 실패하는 테스트 작성**

```python
def test_specific_behavior():
    result = function(input)
    assert result == expected
```

- [ ] **Step 2: 테스트 실행해 실패 확인**

Run: `pytest tests/path/test.py::test_name -v`
Expected: FAIL with "function not defined"

- [ ] **Step 3: `exact/path/to/file.py`에 `function(input: InputType) -> ResultType` 구현**

시그니처와 테스트가 선택을 남길 때만 한 줄로 접근 방식을 적는다
(어떤 라이브러리 호출, 어떤 자료구조). 그들이 정하지 못하는 알고리즘에만
코드 블록을 쓴다.

- [ ] **Step 4: 테스트 실행해 통과 확인**

Run: `pytest tests/path/test.py::test_name -v`
Expected: PASS

- [ ] **Step 5: 커밋**

```bash
git add tests/path/test.py src/path/file.py
git commit -m "feat: add specific feature"
```
````

## 단계에 들어가는 것

단계는 구현자가 그로부터 정확히 하나의 합리적인 것을 쓸 수 있을 때 완성이다.
그게 전부다: 모호하지 않게, 완전하지 않게. 단계 종류마다 모호하지 않게 만드는
것만 담고 그 이상은 담지 않는다:

- **테스트 단계:** 테스트 이름과 assertion을 코드로, 스펙의 정확한 값을 넣어서.
- **코드 단계:** 정확한 시그니처(이름·파라미터·반환 타입), 파일 위치, 스펙이 고정하는 값. 몸통은 구현자가 쓴다. 몸통은 시그니처와 테스트가 정하지 못하는 알고리즘이나 스펙이 고정하는 정확한 카피에만 쓴다.
- **검증 단계:** 실행할 명령과 통과를 의미하는 출력.
- **다른 태스크 참조:** 그 태스크의 Interfaces 블록이 무엇을 쓸지 말해준다. 계획서는 그 태스크의 코드를 반복하지 않는다.

계획서는 구현자가 혼자 내릴 수 없는 결정들의 집합이다. 설명하는 코드보다 긴
계획서는 코드를 쓴 것이지 계획을 쓴 게 아니다. 아무것도 결정하지 않는 줄
("TBD", "엣지 케이스 처리", "적절한 검증 추가", "위 내용에 대한 테스트 작성",
어떤 태스크도 정의하지 않는 타입·함수)은 반대 실패이며, 셀프 리뷰가 둘 다 잡는다.

## 셀프 리뷰

계획서를 다 쓴 뒤, 스펙을 새 눈으로 보고 계획서와 대조한다. 서브에이전트
파견이 아닌 직접 실행하는 체크리스트다.

**1. 스펙 커버리지:** 스펙의 각 섹션/요구사항을 훑는다. 구현하는 태스크를 가리킬 수 있는가? 빠진 것을 나열한다.

**2. 단계 스캔:** 모든 단계는 구현자가 정확히 하나의 합리적인 것을 쓸 수 있게 해야 하고, 그 이상을 담으면 안 된다: 아무것도 결정하지 않는 줄은 빠짐이고, 시그니처와 테스트가 이미 정한 함수 몸통은 전사다. 둘 다 고친다.

**3. 타입 일관성:** 이후 태스크에서 쓴 타입·메서드 시그니처·프로퍼티 이름이 이전 태스크에서 정의한 것과 일치하는가? Task 3에서 `clearLayers()`라 부르고 Task 7에서 `clearFullLayers()`라 부르는 것은 버그다.

**4. Review Focus:** 스펙이 암시하는 입력 클래스·실패 모드마다, 그것을 다루는 태스크의 테스트가 있는가? 가장 맞닥뜨릴 가능성 높은 5개를 Review Focus 섹션에 넣고, 각 줄에 소유 태스크의 테스트를 추가한다. 빈 섹션은 건너뛴 게 아니라 확인해서 없다는 뜻이다.

**5. 비율:** 계획서 길이와 스펙 길이를 비교한다. 스펙의 몇 배인 계획서는 계획이 아니라 프로그램 전사다. 코드 블록이 문서의 대부분이면 몸통을 시그니처로 바꾸고, 각 단계가 여전히 모호하지 않은지 확인한다.

문제를 찾으면 그 자리에서 고친다. 재리뷰는 필요 없다 — 고치고 넘어간다. 태스크 없는 스펙 요구사항을 찾으면 태스크를 추가한다.

## 실행 인계

계획서를 저장하고 셀프 리뷰한 뒤, 상대방이 읽을 수 있게 링크한다. 이미 실행
방식을 명시했다면 계획서 리뷰를 요청하고 원하는 바를 담았는지 확인한다 — 리뷰
전까지 구현하지 않고, 정해진 방식을 쓴다. 그렇지 않으면 계획서 리뷰와 실행
방식 선택을 요청한 뒤 구현한다.

**실행 방식이 정해지지 않았을 때:**

**"계획서 완성 — `docs/superpowers/plans/<filename>.md`에 저장했습니다. 검토해 주세요. 실행 방식을 선택해 주시겠어요?**

- **Subagent-driven** - 태스크마다 새 서브에이전트가 구현하고 새 리뷰어가 다음 태스크 전에 검증, 마지막에 전체 브랜치 리뷰. 가장 철저. 태스크·리뷰마다 새 컨텍스트 비용.
- **Native** - 내가 이 세션에서 전부 직접 구현하고, 마지막에 새 리뷰어 한 명이 전체 브랜치를 검토. 가장 저렴하고 빠르다. 끝까지 독립 리뷰 없음. 계획서가 설계를 갖고 있으므로 중간급 세션 모델로도 잘 돌아간다.

**이 계획에는 <둘 중 하나>를 권장합니다 — <한 문장 근거: 태스크 간 인터페이스 의존도, 태스크 수, 출고된 실수의 비용>. 계획서가 원하는 바를 담았는지, 어떤 방식으로 진행할지 알려주세요."**

**실행 방식이 이미 정해졌을 때:**

**"계획서 완성 — `docs/superpowers/plans/<filename>.md`에 저장했습니다. 검토해 주세요. 원하는 바를 담았나요?"**

**Subagent-driven을 선택하면:**
- **필수 하위 스킬:** subagent-driven-development 스킬 사용

**Native를 선택하면:**
- **필수 하위 스킬:** executing-plans 스킬 사용
