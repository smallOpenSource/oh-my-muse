# Architecture Survey

## Purpose

- **측량사는 암초를 지도에 그릴 뿐, 준설할지는 선장이 결정한다.** 서베이는 "이 저장소의 어디가 바꾸기 어려워졌고, 무엇을 깊게(deepen) 만들면 좋아질지"를 증거와 함께 보고하고 멈춘다. 코드를 고치지 않는다.
- 서베이 시점: 활발한 개발 며칠마다 주기적으로, 또는 한 티켓 묶음이 랜딩한 뒤. 예정 외 시점: "지난주보다 고치기 어려워졌다"고 느껴질 때(수정 하나에 건드리는 파일이 너무 많음, 한 호출자를 위해 인터페이스가 비대해짐, 무관한 이유로 테스트를 함께 고쳐야 함).
- 선택 인자: 조사할 디렉토리·영역을 좁힐 수 있다. 없으면 저장소 전체.

## Workflow

1. **원칙 읽기** — 저장소의 아키텍처 원칙(`CLAUDE.md`, ADR)과 `docs/standards/architecture.md`의 seam/deep module 정의를 읽는다.
2. **모듈 그래프 탐색** — 방향이 없으면 커밋 히스토리를 먼저 읽고 자주 등장하는 핫스팟에 가중치를 둔다(미래 수정이 닿을 곳에 깊어짐의 효과가 크다). 히스토리가 산발적이면 범위를 넓힌다.
3. **세 가지 발견 클래스 탐색** — 각 후보에 **파괴 테스트(demolition test)** 적용: 모듈을 제거하면 그 복잡도가 사라지는가(유니폼 입은 통과 경로 — 발견 아님), 아니면 호출자들에 다시 나타나는가(하중을 지탱함 — 발견):
   - **얕은 모듈(Shallow modules)** — 넓은 인터페이스, 얇은 동작. 호출자가 모듈보다 더 많이 안다.
   - **가설적 경계(Hypothetical seams)** — 정확히 하나의 어댑터만 건너는 경계로, 두 번째 호출자가 없음. 호출자 수 세기로 확인 가능.
   - **잘못된 경계 뒤의 로직** — 자신의 데이터를 소유하지 않은 경계 반대편에 사는 동작.
4. **보고서 작성** — 후보를 레버리지 대비 리스크로 순위 매긴다. 후보마다 포함할 것:
   - **Evidence** — 인터페이스·호출자·동작의 `file:line`.
   - **The deepening move** — 무엇을 깊게/병합/이동할지 한 문장으로.
   - **The risk note** — 무엇을 건드리고 무엇이 깨질 수 있는지.
   - 저장소 공통 어휘로 명시: **severity**(얕음이 유발하는 마찰), **confidence**(서베이 발견은 휴리스틱이라 기본적으로 낮음), **actionable**(보고서만으로 착수 가능한지).
   - 마지막에 **top recommendation** — 가장 먼저 깊게 만들 후보 하나와 이유. 선장은 암초 전체가 아니라 한 장의 카드만 읽는다.
5. **핸드오프** — 보고서는 결정 입력이지 작업이 아니다. 후보는 미션 브리프(launch Phase 1)나 다음 작업의 심문(grill) 재료로 전달한다. 선장이 즉시 행동을 원하면, top recommendation이 바로 디자인-트리 인터뷰의 첫 질문이 된다(인터뷰가 결정하고, 실행은 launch의 게이트를 거친다). **서베이는 어떤 경우에도 직접 수정하지 않는다.**
   - 하중 있는(load-bearing) 이유로 기각된 후보는 ADR로 제안한다(다음 서베이가 같은 암초를 다시 지명하지 않도록). 이유 없이 기각된 후보는 그냥 가라앉힌다.

## Output Contract

- 순위 매긴 후보 목록: Evidence(file:line) + deepening move + risk note + severity/confidence/actionable.
- Top recommendation 한 장.
- 수정된 파일: **없음** (완료 정의: 보고서가 존재하고 파일 수정이 없어야 함).

## Operating Rules

1. **코드 수정 금지** — 서베이는 리팩터링하지 않는다. "따끈할 때"도 안 된다.
2. **게이트가 아님** — 보고서 때문에 무엇도 블록되지 않는다.
3. **drydock `--check` 감사와 분리** — `--check`는 기계적으로 확인 가능한 고신뢰 발견만. 아키텍처 판단은 저신뢰 휴리스틱이므로 섞지 않는다.
4. **로그북(ADR) 충돌** — 기존 ADR과 모순되는 후보는 마찰이 실제로 있을 때만 지명하고, 해당 ADR과 상황이 바뀐 이유를 카드에 명시한다. 이론적 충돌은 보고하지 않는다.
5. **주기 실행** — 주기적 서베이(며칠 간격)가 필요하면 Muse의 `cron`으로 예약한다. 원본의 네이티브 cron 연동 개념은 동일하되, 이 환경의 cron을 사용한다.
6. **시각화(선택)** — 저장소에 diagram 스킬이 있으면 보고서 시각화에 써도 되지만, prose 보고서가 원본(source of truth)이다.
