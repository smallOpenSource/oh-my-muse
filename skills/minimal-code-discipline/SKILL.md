# minimal-code-discipline — 최소 코드 규율 (YAGNI 사다리)

## Purpose

코드 변경을 계획·작성할 때 적용하는 최소 코드(YAGNI 사다리) 규율. diff를 작고 자명하게 유지하면서, 사용자를 지키는 검사는 절대 줄이지 않는다. `ai-slop-cleaner`가 착륙한 뒤 치운다면, 이 스킬은 애초에 쓰이지 않게 막는다.

**사용하지 않을 때**: 사용자가 명시적으로 넓고 풍성하거나 미래 대비 빌드를 요청한 경우(명시 범위가 우선), 사용자가 throwaway라 표시한 탐색 스캐폴딩, 최소화가 Non-Negotiables를 건드릴 때.

## Workflow

### Step 1 — 변경 정당성 확인

- **존재 우선**: 이 변경이 존재해야 하는가? 가상의 미래 수요를 위한 작업은 건너뛴다.
- **먼저 이해하고 줄이기**: 영향받는 코드를 읽고 실행 경로를 따라간 뒤, 문제를 이해한 상태에서 가장 짧고 올바른 diff를 낸다.

### Step 2 — 작성 중 규율

- **재사용 우선**: 새로 쓰기 전에 코드베이스에서 기존 헬퍼·타입·패턴을 검색. 몇 파일 옆에 있는 헬퍼를 복사하지 말고 재사용하거나 한 곳으로 추출.
- **의존성 사다리**: 표준 라이브러리 → 플랫폼 네이티브 → 이미 설치된 의존성 순. 손으로 쓰는 코드는 최후 수단. 몇 줄로 되는 일에 새 의존성을 들이지 않는다(사용자가 명시 요청·승인한 경우 제외).
- **지루함이 영리함보다**: 뻔하고 자명한 코드를 영리한 코드보다 선호.
- **천장을 표시**: 의도적 단순화는 "받아들인 한계 + 언제 교체할지"를 짧은 코멘트로 기록.
- **증상이 아닌 근본 원인**: 버그는 모든 호출자가 공유하는 근본 원인을 고치지, 보고된 증상마다 별도 패치를 붙이지 않는다.

### Step 3 — 보고 전 검증

- 모든 Non-Negotiables가 온전한가 (아래)
- 추가된 모든 줄이 자리를 차지할 자격이 있는가(가상의 일반화·중복 헬퍼 없음)
- diff가 문제를 올바르게 푸는 가장 짧은 형태인가
- 테스트가 여전히 통과하고, 요청 외 동작 변화가 없는가

## Output Contract

완료 보고 시 다음을 포함한다: 무엇을 바꿨는지(파일·diff 요약), 무엇을 일부러 바꾸지 않았는지(천장 표시 포함), Non-Negotiables 확인 결과, 테스트 결과.

## Operating Rules

**절대 줄이지 않는다 (Non-Negotiables)**

- 신뢰 경계를 넘는 곳의 검증(validation)
- 데이터 손실을 막는 에러 처리
- 보안 컨트롤
- 접근성 기본
- 사용자가 명시 요청한 범위

**한계**

- 이 규율은 "사용자가 명시적으로 요청한 넓은 범위"를 이기지 못한다. 명시 범위가 우선.
- 동반 규율: 사람이 읽는 문서는 `agent-doc-discipline`, 사람에게 말하는 문장은 `minimal-prose-discipline`을 적용한다.
